# Ledger of Cra's design decisions (as of 2026-10-30)

Translated from `cra-ledger.ja.md` (2026-10-30). The English file is the source of truth from now on.

Subject: https://github.com/VictorKildahl/cra (MIT, HEAD = 37a87aad, 2026-10-29). The first commit is from 2026-10-24 (fac5c687); the history has 40 commits, and the releases are Cra 0.1.0–0.1.19 plus 4 CEF builds. The design was replaced several times within 5 days.

Notes on reading:

- In the evidence column, "`path:line`" is a line number in the file at HEAD. `arc-RE` refers to `docs/arc-reverse-engineering.md`.
- "Ararat" was evaluated under these premises: fork Chromium and put our own layer inside the tree (the ArcCore approach), UI in Swift/AppKit, core in Rust.
- Terms: Alloy style = CEF's execution mode for embedding (has no Chrome UI). Chrome style = the execution mode that uses Chrome's own Browser and Views inside CEF (extensions and Chrome's DevTools work).

## 1. Structure diagram

### SwiftPM targets (`Package.swift`)

| Target | Kind | Language | Dependencies | Role |
|---|---|---|---|---|
| `Cra` | executable | Swift | `CraCEF`, Sparkle (vendor/sparkle, linked directly with `-F`) | The app itself. AppKit window, sidebar, command bar, state, import, updates |
| `CraCEF` | library | Objective-C++ (C++20, `-fno-rtti -fno-exceptions`) | `libcef_dll_wrapper` (vendor/cef built with CMake), AppKit, IOSurface | The boundary between Swift and CEF. The public API is only the 4 classes and 1 protocol in `Sources/CraCEF/include/CraCEF.h` |
| `CraHelper` | executable | C++ | `libcef_dll_wrapper` | Chromium child processes (renderer, GPU, utility). Enters the sandbox with `CefScopedSandboxContext` before loading the framework (`Sources/CraHelper/main.cc:9-20`). build.sh copies it into 5 Helper.app bundles |
| `CraDockTile` | dynamic library | Swift | AppKit | Dock tile plug-in. Keeps the Dock icon after the app quits (d1a43cb5) |

The dependency direction is one-way: `Cra → CraCEF → CEF(libcef)`. `Cra` sees only the types in `CraCEF.h` (`CraBrowser`, `CraBrowserDelegate`, `CraCEFRuntime`, `CraApplication`). No CEF C++ types appear in Swift.

### The `CraCEF.h` boundary (the surface visible from Swift)

- `CraBrowser` (one tab's Chromium browser): creation (URL, incognito, profilePath), navigation, find, zoom, DevTools, PiP, `sendDevToolsMethod` (per-tab CDP), and two placements: `containerView` (for Alloy) and `hostWindow` (for Chrome style) (`CraCEF.h:86-169`).
- `CraBrowserDelegate`: receiver for title, URL, loading, favicon, theme color, background color, fullscreen, new-tab requests, popups, DevTools placement, keys (reserved keys and unhandled keys), downloads, and permission requests (`CraCEF.h:27-84`).
- `CraCEFRuntime` (process-wide): initialization, run loop, switching Chrome style, own context menus, ad blocking, HTTPS-Only, handoff on multiple launches, a receiver for "stray pages" (tabs opened by extensions), per-browser CDP pipe, and fetch using the profile's cookies (`CraCEF.h:171-248`).
- `CraApplication`: the `NSApplication` subclass CEF requires. ⌘-key dispatch and replacing the accessibility window are also done here (`CraCEF.mm:2093-2175`).

### 3.2 Caused by Chromium, remaining in a fork too (for reference)

- WebRTC mDNS and the Local Network prompt (ledger 27).
- Synchronous XPC every 500 ms for Bluetooth (`ChromiumBluetoothCache` swizzles `IOBluetoothDevice`). In a fork this becomes a fix in Chromium's source instead of a swizzle (`Services/ChromiumBluetoothCache.swift`, a1c6c33e).
- The problem where imported cookies with `has_cross_site_ancestor = 0` do not match Chromium's UPDATE and DELETE (a0572f5e). Remains as long as cookies are imported from other browsers.

### 3.3 Unrelated to CEF (Cra's own decisions or mistakes)

- The mistake of starting with `--use-mock-keychain` (ledger 24).
- The in-house build to include video codecs (ledger 5). In a fork this is one line of build configuration, not a workaround.
- Symlinking native messaging hosts (ledger 29). Remains as long as we have our own bundle id.
- Reading `AuthServerAllowlist` from Chrome's and Edge's policy domains (ledger 28). It originated because CEF does not read policy, but a fork's policy mechanism reads the domain of our own bundle id, so whether to honor settings IT deployed for Chrome remains a product decision.
