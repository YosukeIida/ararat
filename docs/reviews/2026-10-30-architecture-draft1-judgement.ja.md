# アーキテクチャ draft 1 に対する Codex のレビューの判定

この文書は `2026-10-30-architecture-draft1-judgement.md` の日本語訳である。内容が食い違うときは英語版に従う。

レビュー: `2026-10-30-architecture-draft1-codex.md`（Codex `gpt-6.1-sol`、effort medium、labteam アカウント、読み取り専用）。
判定者: Claude Opus 5.5、effort medium。結果: `docs/architecture.md` の draft 2。

| # | 指摘 | 判定 | draft 2 での変更 |
|---|---|---|---|
| 1 | セキュリティの保守のモデルがない | 修正 | 4.9 を新設: upstream の日次の検出、パッチの遅延の上限、緊急ビルド、日常的な使用の前に必須とする更新の経路と評判の検査。セキュリティのための更新の事前承認はオーナーの判断とする（14） |
| 2 | 同期のプロトコルが規定されていない | 修正 | 8.2 で次の要件を課した: ランダムな 192 ビットの nonce を用いた XChaCha20-Poly1305、デバイスごとの署名鍵、PAKE で認証したペアリング、コンテンツ鍵とは別のリレー用の資格情報、リプレイのチェックポイント、デバイスの削除時の epoch による鍵の更新。バージョン付きのプロトコル仕様を、同期のコードを書く前の関門とする |
| 3 | tombstone の期限切れにより削除が復活する | 修正 | tombstone は、デバイスの退役、epoch、スナップショットによる再参加の義務付けが実装されるまで無期限に保持する。incarnation とシーケンス番号の保護は、最初の同期のリリースから導入する |
| 4 | レコード単位の LWW（last-writer-wins）がツリーを壊しうる | 修正 | 項目ごとに所属のレジスタを 1 つ置く（parent id + fractional order key）。子のリストは導出する。循環、親の欠落、削除と編集の競合に対して決定的な修復を行う。ツリーの不変条件のテストを追加した。phase 1 のモデルのコードはこの表現に移行し、Arc のインポーターはこの表現に変換する |
| 5 | Chrome とコアの間にクラッシュ時の一貫性がない | 修正 | 5.2: すべての revision にエンジンの epoch を含める、安定したタブ id、起動時のスナップショットと照合、明示したクラッシュ時に失われうる範囲、workspace の変更と送信用の同期のレコードを 1 つの SQLite トランザクションで書き込む、ディスクの容量不足への対処、SQLite の backup API によるバックアップ |
| 6 | セッションのペイロードの所有者が欠けている | 修正 | 4.6/5: エンジンは Chromium のセッションのシリアライズ（ナビゲーションスタック、セッションストレージ）を維持し、コアの項目 id をキーとする。タブの状態ごとの保持期間を定めた。無効にするのは Chrome のウィンドウの自動復元だけである |
| 7 | シークレットモードの永続化の境界 | 修正 | off-the-record の識別をエンジンの契約に含める。コアは off-the-record に対する永続的な操作と同期の操作を 1 か所でまとめて拒否する。テストを列挙した |
| 8 | 1 つのウィンドウ内の複数の `Browser` と、拡張から見たウィンドウの意味論 | 修正 | 4.6 で対応関係を定めた（表示中のプロファイルの `Browser` が current かつフォーカスを持ち、それ以外はフォーカスなしを報告する）。spike のテストを追加した |
| 9 | ウィンドウ間のタブと分割ペインのライフサイクル | 修正 | 4.6 に、ページの所有と移動、プレースホルダー、split のフォーカス、クローズの意味論を追加した。いずれも spike の対象とした |
| 10 | 削除した Chrome の UI がセキュリティ上の責務を担っている | 修正 | 4.6 に、spike で完成させる責務の表を追加した。受け入れ条件に、権限の拒否、フルスクリーンの解除、外部プロトコル、IME、⌘L の後の貼り付け、アクセシビリティを追加した |
| 11 | 移植可能なブラウザの契約がない | 修正（調整あり） | live-tab coordinator を Rust のコアに移し（Swift は薄いアダプターになる）、Windows/Linux でそれを再利用する。パスワードは、ブラウザプロセス内でゼロで消去するバイトバッファとしてエンジン → コアに渡し、コアが封緘する。DRM の決定を phase 4 の API 凍結の前に移した。汎用のページエンジンの抽象化は、第 2 のエンジンを選ぶまで追加しない |
| 12 | エンジンの成果物の同一性が不完全 | 修正 | 4.7: コミットしたビルド入力のマニフェスト（Chromium のコミット、Helium のタグ、DEPS のハッシュ、GN args、Xcode/SDK、アーキテクチャ）を成果物のキーとする。ダイジェストと provenance を公開する。Corresponding Source でツリーを再構築できる |
| 13 | 拡張のインポートの出所 | 修正 | Store の拡張は Web Store から再インストールする。パッケージ化されていない拡張のインポートには明示的な承認を要する。ネイティブホストのマニフェストと実行ファイルを検証する |
| 14 | compositor の所有が欠けている | 修正 | 計測（最初のフレーム、バックグラウンドの活動、オクルージョン、リサイズ、split、ディスプレイの変更）に基づいて spike で決定する |
| 15 | tracking area ではウィンドウ外のポインタを追跡できない | 修正 | 7: ウィンドウ内は tracking area を用いる。サイドバーの表示中は、ウィンドウ外でポインタをサンプリングし、非アクティブになったときに停止する |
| 16 | ロードマップでリスクの検証が遅すぎる | 修正 | ロードマップを並べ替えた: 署名の識別情報と表示ありの検査を含む、エンジン・コア・UI の最小限の縦断スライスを UI の構築より前に置く。クラッシュと再起動のテスト、オフラインでの同期のテストを追加した。Windows と Linux の関門を分けた |
| 17 | Helium の利点が実証されていない | 修正 | Helium は暫定とする。phase 2 で、固定したパッチの一覧、セキュリティ上の帰結（Helium のフラグは Safe Browsing を無効にする）、1 回のリベースの計測に基づき、Chromium + ungoogled-chromium と比較して決定する |
| 18 | ポップアップに関する記述が誇張されている | 修正 | 記述を改めた。生成経路を列挙し、それぞれ個別にテストする |
| 19 | ObjC の前例の帰属が誤っている | 修正 | Dia の API は mojom から生成されており、こちらの API は手書きである。スレッド、無効化、キャンセル、所有の規則を追加した |
| 20 | 性能の関門の記述 | 修正 | 1 つのコントローラーが、分離した対照と候補のプロセスを交互に実行する |

却下した指摘はない。主要な選択（エンジンの直接の組み込み、型付きの ObjC API、macOS ではエンジンが Rust をリンクしないこと、SQLite、ブラインドリレー、AppKit/SwiftUI の分担、iPhone での WKWebView）についての Codex の要約は draft 1 と一致している。Helium は条件付きの扱いになった。

次の作業: 複数の節（同期、状態、ロードマップ）が大きく変わったため、draft 2 について Codex による 2 回目のレビューを行う。
