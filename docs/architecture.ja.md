# Ararat のアーキテクチャ

この文書は `architecture.md`（draft 2）の日本語訳である。内容が食い違うときは英語版に従う。

状態: draft 2、2026-10-30。日本語訳: `architecture.ja.md`。レビューの履歴: `reviews/`。

本文書は、技術の選択、レイヤー、密結合にする部分と分離する部分、状態と同期の仕組み、ロードマップを定める。本文書は次の 3 本の調査ノートに基づく。

- `research/ardia-ledger.md`: Ardia（Chromium fork、React Native の UI）における設計判断と書き直し。
- `research/cra-ledger.md`: Cra（Swift + CEF）における設計判断と、Cra が必要とした CEF の回避策。
- `research/arc-dia-components.md`: 公開されたリバースエンジニアリングから収集した、Arc と Dia のコンポーネントの一覧、データ形式、Chromium の継ぎ目（seam）。

「Ardia ledger 1.4」のような参照は、これらのノートの節を指す。

## 1. 目的と制約

Ararat は、Arc のワークフロー（space、ピン留めタブと Today タブ、favorites、フォルダ、archive、command bar、Little Arc、Air Traffic Control、split view）と Yab の縦タブの挙動を、Chromium 上で Chrome 拡張とともに実現するブラウザである。

オーナーが定めた制約は次のとおりである。

- macOS を最初に対象とし、UI は Swift によるネイティブ UI とする。
- エンジンは Chromium fork とし、Chromium のツリー内に独自のレイヤーを置く。
- Windows、Linux、iPhone は後から対応する。これらを追加するときに構造の書き直しを要してはならない。
- クロスプラットフォームのコアは Rust で実装する。
- 同期は独自のサーバーを経由し、アカウントやログインを一切必要としない。
- ライセンス: GPL-3.0。
- Arc、Dia、Yab はクローズドソースである。公開された分析と、各製品の利用規約が認める静的解析を用い、コードやアセットは一切複製しない。Ardia のコード（GPL-3.0）は出典を明記したうえで再利用してよい。

| エンジンのベース | Chromium と ungoogled-chromium のパッチセット（オーナーの選択、2026-11-04） | Helium は ungoogled-chromium の上に作られており、追加の変更の多くは Ararat が外すもの（パスワードマネージャーの削除、キーチェーンの名称変更、Sparkle、オンボーディング、!bangs、Web Store のプロキシ）である。コーデックは GN args で得られ、パッケージングは自前のものに置き換える。Ardia は Helium に移った後、Helium と ungoogled の動作を元に戻すパッチを 18 件持ち、移った理由は記録されていない（Ardia ledger 1.2） | 4.2 |

| run loop | Chromium がプロセスとメインループを所有し、AppKit の UI はその内部で起動する | 外部からのポンプに起因するバグを排除する（Ardia ledger 1.1） | 4.5 |

| コア | Rust の crate `ararat-core`、SQLite のストレージ、Swift 向けの UniFFI バインディング、C++ 向けの C ABI | macOS、Windows、Linux、iPhone で同一のコアを使用する | 6 |

| 同期 | エンドツーエンド暗号化とし、アカウントを必要としない。独自サーバーは、認証済みで追記のみの blob を中継するブラインドリレーとする。デバイスはリカバリーフレーズ、または PAKE（パスワード認証鍵交換）で認証したペアリングコードで参加する | 「独自サーバー、ログインなし」の条件を満たす。Chromium の同期エンジンや共有フォルダが存在しない環境（iPhone、Windows）でも動作する | 8 |

## 3. レイヤーとリポジトリの構成

```
ararat/
  core/            Rust workspace: ararat-core (model, rules, coordinator, import, sync client), ararat-ffi (UniFFI + C ABI)
  server/          Rust: the sync relay (phase 8)
  engine/
    build-inputs.toml  the pinned build identity (4.7)
    ararat/        our in-tree layer, copied to //ararat/core
    chrome/        our files under //chrome/browser/ararat
    patches/       series + patches against the base
    scripts/       apply（series のあとでレイヤーを rsync）、series-check、gen、build、smoke
  macos/           one SwiftPM package
    Sources/ararat_ffiFFI/  C module for the core's UniFFI header; links the Rust static library
    Sources/AraratKit/      Swift adapter over the core bindings (generated) and, later, the engine API
    Sources/AraratUI/       AppKit + SwiftUI components (library)
    Sources/AraratHarness/  UI harness: real components on real core data, a placeholder where the page goes
    scripts/build-core.sh   builds the core and regenerates the bindings
    Sources/Ararat/         アプリの起動実行体: framework を読み込み、ChromeMain を呼ぶ
    scripts/bundle-app.sh   エンジンの Chromium.app を Ararat.app に組み、ad-hoc で署名する
  docs/
```

harness はアプリの代替ではなく恒久的な開発ツールであり、UI の作業が Chromium のビルドを待つことはない。Cra の command file と Ardia の dev harness も同じ役割を果たしている。

### 依存の方向

```
macOS App ──► AraratUI ──► AraratKit ──► ararat-ffi ──► ararat-core
                               │
                               └──► engine ObjC API (//ararat/core) ──► Chromium //chrome
```

- `ararat-core` はプラットフォーム固有のものに一切依存せず、エンジンや UI を呼び出さない。コアが判断し、アダプターが実行する。
- `AraratUI` はエンジンを直接呼び出さない。エンジンとコアのハンドルを保持するのは `AraratKit` だけである。
- `AraratKit` は薄いアダプターである。`AraratKit` はエンジンのトランザクションをコアの coordinator へ転送し、coordinator が返すエンジンのコマンドを実行する。規則はコアに置くため、Windows と Linux ではアダプターだけを再実装する。
- macOS では、エンジンはコアをリンクせず、アダプターが同一のブラウザプロセス内で両者を橋渡しする。Windows と Linux では、Views の UI が C ABI を介してコアをリンクする（10 節）。
- Chrome のファイルが参照するのは独自の hook ヘッダー（4.3）だけであり、独自のクラスは参照しない。

## 4. エンジン

### 4.1 密結合にする部分と分離する部分

| 部分 | 結合 | 場所 | 規則 |
|---|---|---|---|
| 独自の `BrowserWindow`、`BrowserDelegate`、UI の seam の実装、セッションの永続化、ObjC API | 密結合、ツリー内 | `//ararat/core`、`//chrome/browser/ararat` | 新規ファイルのみとする。Chrome の GN ルールでビルドする |
| Chrome 自体のファイルへの編集 | 最小限、hook として分離 | `engine/patches/` | 各編集は、1 つの共有ヘッダーで宣言する関数ポインタの hook とする。1 パッチにつき 1 つの関心事とする |
| ベースのパッチセット（ungoogled-chromium） | 取り込み、ガード付き | `engine/patches/series` | スキップリストとガードにより、スキップしたパッチが含まれないこと、およびスキップによって保護している箇所に何も手が入らないことを検査する |
| Rust のコア、同期、インポート | 分離 | `core/` | Chromium の型を使用しない |
| AppKit の UI | 分離 | `macos/` | エンジンとは `AraratKit` を介してのみ通信する |

### 4.2 ベースとパッチの管理

- クリーンな Chromium の revision とベースのパッチセットは、`engine/build-inputs.toml` で別々に固定する。
- ベースは ungoogled-chromium とする（オーナーの選択、2026-11-04。Helium と比べた理由は 1 節）。ungoogled-chromium の全パッチを、維持・スキップ・対抗パッチのいずれかに分け、セキュリティ上の帰結を記した一覧は `docs/research/ungoogled-inventory.md` の 8 節にある。phase 2 では、選択した upstream のパッチと、こちらのパッチ（component updater を保つ対抗パッチは同 8.6 節、もう一方は ScreenAI の sandbox パラメータを除く `ararat/remove-screenai-sandbox-parameter.patch`）をビルドする。評判のソース（14）をオーナーが決めるまで、Google Safe Browsing をビルドに残すので、9 の拡張の kill switch は有効のままである。ドメインの置き換えとバイナリの削除は行わない（我々の規則、暫定）。固定する版は、phase 2 で 1 回計測したリベース（後述）の後の 157.0.8103.39 である。
- それまでは Helium を暫定のベースとしていた。一覧やリベースで ungoogled-chromium の手間が見込みより大きいと分かった場合は、Helium を比較の候補とし、Ardia に倣ってこちらの選択と衝突するものをスキップする（Ardia ledger 1.2）。
- パッチの順序の唯一の正本は `engine/patches/series` である。パッチ名は関心事を表し、順序を示す接頭辞は付けない。
- パッチの実体は、固定した ungoogled のコミットから `engine/patches/ungoogled/{generic,macos}/` に取り込み、両プロジェクトの BSD-3 の LICENSE も合わせて置く。generic のパッチは、ungoogled-chromium の 157 向けの pull request（#4032、2026-11-04 に merge、タグ `157.0.8103.38-1`。merge コミットは取り込み済みの head と同一なので、取り込み直しは不要）の head からバイト単位で同一のまま取り込む。macOS のパッチは 156 の macOS のコミットから取り込み、`disable-crashpad-handler.patch` だけを手で 157 に当て直した。コミットの一覧は `engine/patches/README.md` にある。`engine/patches/ararat/` はこちらのパッチを置く場所である（我々の規則）。
- `series` 全体を適用・検証するのは `engine/scripts/` の bash スクリプト群である: `env.sh` が共通の環境とユーティリティを担い、`fetch` がタグの取得と DEPS 同期、`apply` がリセットと no fuzz の系列適用に加えてレイヤーのコピー（`engine/ararat/` → `src/ararat/core/`、`engine/chrome/` → `src/chrome/browser/ararat/`）、`series-check` が系列のバイトとコピーされたレイヤーの検証、`gen` が args と GN の生成、`build` がロックと autoninja、`smoke` が headless 確認（我々の規則）。
- `series-check` は、系列が触る全ファイルとコピーされたレイヤーのファイルの SHA-256 を、前回の正常な apply で記録したマニフェスト（`engine/patch-state.sha256`, `engine/` にコミットする）と、読み取り専用で比較し、コピー先のレイヤーディレクトリの余分なファイルも拒否する。リセットも適用もせず、マニフェストが別の series のために記録されたものであるときも拒否する。エンジンのビルドの前に毎回実行する。`build` は自身の前にこれを実行し、1 バイトでも違えば、ツリーに触れずに「`apply` を実行せよ」と言って止まる。`build` はリセットも再適用もしない（我々の規則）。
- `apply` は、パッチ済みのファイルをディスク上のバイトと違うときにだけ書く。ツリーが前回の正常な apply のバイトに一致し、series も変わっていなければ何も書かず、mtime をすべてそのままにする。そうでなければツリーを pristine にリセットし（src と系列が触るすべての DEPS リポジトリ）、series を順に fuzz なしで適用し、マニフェストを書き直す。最初の失敗でパッチ名とファイル名を出して止まり、ツリーを半適用ではなくリセット済みで残す（我々の規則）。
- 対抗パッチの `ararat/restore-component-updater.patch` は、`block-requests` の `components/update_client/update_checker.cc` の 1 hunk だけを打ち消すので、apply の後にはこのファイルが素の Chromium とバイト単位で同一に戻る（156 で確認済み）。もう一方の `ararat/remove-screenai-sandbox-parameter.patch` は、ScreenAI サービスの sandbox パラメータ（コンポーネントのバイナリのパスを渡す branch）を `chrome/browser/chrome_content_browser_client.cc` から除く。
- ソースは tarball でなく、固定タグの git + gclient と Chromium 固有の固定ツールチェーンから取り、ungoogled の pruning.list は実行しない（gclient が置くプリビルドのツールチェーンを消すから）（我々の規則）。
- PGO: 156 の固定の `chrome/build/mac-arm.pgo.txt` が指す mac-arm のプロファイル（約 88.9 MB）は公開の optimization-profiles バケットにあり、gclient のフックが取得できる。ただし `.gclient` で `checkout_pgo_profiles` を立てたときだけで、`chrome_pgo_phase=2` のままでは `gn gen` が拒否する。phase 2 は `chrome_pgo_phase=0` で走り、プロファイルは取得していない。約 89 MB の取得を払うかどうかは design の判断である（我々の規則）。
- series の適用は 156 のツリーで 11 秒であった（2026-11-05、リセット込み）。mtime を保つ再適用は何も書かず、約 10 秒、すべて検証の時間である。
- 157.0.8103.39 へのリベース（2026-11-05、1 回計測）: 取得と DEPS の同期に 5 分 45 秒かかった。当たらなくなった generic の 14 本は、ungoogled-chromium の 157 向けの pull request（#4032、157.0.8103.38 向け）の版に替えた。`disable-crashpad-handler.patch` は、crashpad の `InitialStart` に `embedder_port` 引数が増えたので、手で当て直した。その後、パッチが fuzz なしで 129 ファイルに当たった。取得の開始からおよそ 8 分である。こちらのパッチはそのまま当たった。
- Chrome のファイルへの大きな編集は、新しいクラスと小さな hook に書き直す（Ardia は 1,012 行の PiP パッチをこの方法で書き直した）。
- 指標はパッチの数ではなく、Chrome のファイル内の hunk の数とする。

### 4.3 Hook

hook は `ararat_hooks.h` で宣言する `g_ararat_*` の関数ポインタである。パッチを当てた Chrome のファイルはこのヘッダーをインクルードするが、`g_ararat_is_window` と `g_ararat_history_deleting` は例外である。前者は read-anything controller、後者は HistoryService でヘッダーを使わずに定義するため、宣言とのシグネチャの違いはコンパイル時に検査されない。履歴削除 hook は HistoryService が明示的な削除を予約する前に呼ばれる。hook が未設定のとき、Chrome は標準どおりに動作する。今日の一覧: `g_ararat_is_window` は read-anything の viewless 経路で独自ウィンドウを識別する。`chrome/browser/chrome_content_browser_client.cc` の `g_ararat_add_browser_main_extra_parts` は、client が作ったブラウザのメインパーツを独自レイヤーに渡し、レイヤーは `AddParts` を通じて独自の `ChromeBrowserMainExtraParts` を加える。`chrome/browser/ui/browser.cc` の `g_ararat_create_browser_window` は常時設定し、対象の Browser を独自 host に渡す。`g_ararat_reopen`、`g_ararat_dock_menu`、`g_ararat_open_urls` は Dock からの再オープン、Dock メニュー、外部 URL を扱い、`g_ararat_shown_browser` は AppController に表示中の Browser を返す。`g_ararat_create_permission_prompt` は権限要求を独自のタブモーダルプロンプトに渡す。window factory の hook は `Browser*` ではなく `BrowserWindowInterface*` を受け取る。upstream は呼び出し側を interface へ移すため `browser.h` の利用を `browser_header` の visibility で制限しており、独自レイヤーには interface だけで足りるためである。エクスポートする名前は、`ararat.exports`（リンカの `-exported_symbols_list`）と、`link-ararat-layer.patch` が `chrome/app/framework.order` に追加するシンボルの両方に並べる。`verify_order.py` は order ファイルにない framework のエクスポートを拒否するためであり、両者の違いはスクリプトが断り、`engine/ararat/` に定義のない名前も断る（我々の規則）。

### 4.4 エンジン ↔ アプリの API

U17b は `openURL:commandId:itemId:profile:external:untrusted:historyStamp:`、`AraratPurgeTabHistory`、`AraratFinishCrashRecovery`、`AraratCheckTabHistoryFile`、`AraratCheckDeleteHistory`、`AraratCheckCrashState`、`AraratCheckCommitProfilePrefs` と、タブの `checkFlushHistory:` を追加する。flush の成功はファイルの atomic write の完了を示す。profile preferences の commit 検査は、crash seed が ready を出す前に Chromium の書き込み完了通知を待つ。

- U27w は `AraratApplySiteDefaults`、`AraratSiteExceptions`、`AraratSetSiteException`、`AraratClearSiteData` を AraratHostAPI.h に加える。設定のペインは通常のプロファイルのすべてに働くため、`ARWindowHostAPI` のメソッドではなく C の関数とする。7 つの既定値は、アプリの同期する `settings` のレコードを各プロファイルの `HostContentSettingsMap` の既定値へ書き込んだもの（後からエンジンが作るプロファイルにも書く）。一覧は 7 種類の pref の提供元の単一 origin の規則である。書き込みはその origin と種類の `SetPermissionSettingDefaultScope`（nil の設定で消す）。サイトの削除は `BrowsingDataRemover` の 1 つの処理で、登録可能ドメインの filter と cookie・DOM storage・cache の mask を渡し、返事は失敗したデータの種類のビットマスクであり件数ではない。`settings-websites` で検査する（我々の規則。実行時の検証は未実施）。

open コマンドは項目のプロファイルを運ぶ。エンジンに届く前にユーザーが space を切り替えても、項目のプロファイルで開く。host delegate の `showProfile` 要求は、そのウィンドウで最後に表示した当該プロファイルの space に切り替える（我々の規則）。

- framework は `//ararat/core` に Objective-C クラスを実装する（たとえば `ARWindowHost`、`ARTab`、および予定している `ARProfile`、`ARExtensions`、`ARDownloads`、`ARAutocomplete`、`ARPasswords`）。Swift はアプリ向け protocol を SwiftPM 経由でインポートし、読み込んだ framework から `AraratWindowHostCreate(contentView, windowId)` を `dlsym` で取得する。host とタブは protocol を通して操作する（我々の規則）。

- タブ API は coordinator の ID を受け取る。アプリは `AraratWindowHostCreate` に workspace の window ID を渡す。`openURL:commandId:itemId:` は open が受け付けられたか（完了またはキューに積まれた）を返し、開いたタブは `-tabs` から live ID（command ID）で探す。`activateWithCommandId:`、`closeWithCommandId:`、`setItemId:` はそのタブを操作する。Browser の破棄中の open は FIFO でキューに入る。完了の transaction にその live ID が含まれない open は失敗したと見なす。受け付けた open が失敗したときは transaction として報告する。それは次の revision で、cause は `Command(<その open の ID>)` であり、strip は現状のままで、Browser が無いウィンドウでは空の strip を運ぶ。拒否された open（host が閉じている、epoch が無い、URL が不正など）は `NO` を返し、何も報告しない。Chrome が作成したタブには `chrome-` を先頭に付けた UUID を割り当て、item ID は付けない。`ARWindowHost` は delegate から page card を取得し、`{epoch, rev, cause, strips}` を delegate に報告する（我々の規則）。
- `pageCardForWindowHost:` は値を返すだけの getter とし、KVO の observer はタブコマンドを非同期に dispatch する（我々の規則）。
- Browser の factory は `create_host` で同期的に host を要求する。openURLs と Handoff は `open_urls` を使う。外部からの open は Chrome の untrusted launch フラグを運び、エンジンは opaque initiator を維持する。strip は opener の live ID、commit 済みの URL とページタイトル、および新たなナビゲーションが commit されたかを運ぶ。タイトルとナビゲーションの変更時にも transaction を送る（我々の規則）。
- feed はエンジンのプロセスごとに、起動時刻に基づく epoch と 1 つの revision を持つ。最初の host に delegate を設定すると、cause が `Engine` の空の rev 0 スナップショットを同期的に報告する。その最初の delegate が設定されるまで、タブコマンドは何もせず、`openURL:` は `NO` を返す。その後の変更ごとに revision を増やす。閉じたウィンドウは cause を `Engine` とする空の strip で報告し、workspace の行を閉じずに live の対応を解除する。省いたウィンドウは変更なしと扱う（我々の規則）。
- 各コマンドは、その cause を持つ transaction をちょうど 1 つ生成する。2 つ目は捨てる（我々の規則）。
- すべてのクラスをメインスレッドに固定する（他のスレッドからの呼び出しはプログラミングエラーであり、debug ビルドでは abort する）。Chrome のオブジェクトをラップするオブジェクトは、Chrome のオブジェクトが破棄された時点で無効化する。ラッパーは Swift が所有し、Chrome のオブジェクトはエンジンが所有する。無効化された `ARTab` へのコマンドは何もせず、エラーを返さない。transaction の通知は初回のスナップショット以降、host を弱参照してメインキューに post する。fullscreen の状態は同期的に通知する（我々の規則）。
- UI が必要とするサービス（パスワード、autofill、拡張、ズーム、検索エンジン、履歴、ブックマーク、ダウンロード）は、独自レイヤーから Chrome のサービスを直接呼び出す。`chrome://` の WebUI ページをスクリプトで操作することはしない（Ardia ledger 1.4）。
- アプリとエンジンは同時に出荷する。互換性のための分岐は設けない。起動時に API のバージョンを 1 回検査し、不一致の場合は abort する。

### 4.5 プロセスと run loop

AppController の hook はメインウィンドウの表示中 Browser を返し、最後のプロファイルとメニューの対象を切り替えに追従させる。native の openURLs と Handoff は、Chrome の safe-profile 経路で検証してから開く（我々の規則）。

- `started` でアプリは workspace を開き、sidebar と page card を `SidebarContainerView` に組み立て、host を生成して engine adapter を接続する。`will_shut_down` で adapter を切り離し、host をメインスレッドで解放する（我々の規則）。
- バンドルの起動実行体（`Sources/Ararat`）が framework を読み込む。ブラウザプロセスは独自の `AraratMain` を呼ぶ（ランチャーのコールバックを保存し、extra-parts の hook を設定して `ChromeMain` を呼ぶ）。ヘルパーは標準の `ChromeMain` を呼ぶ。hook は標準の client のパーツに独自の `ChromeBrowserMainExtraParts` を加え、それらが `PostBrowserStart` でランチャーの `started` コールバックを、`PostMainMessageLoopRun` で `will_shut_down` を呼ぶ。`started` は `PreMainMessageLoopRun` の中で、起動ブラウザが開いた後、メインループが回る前に発火する。ハンドラはループが回っていると見なしてはならない。`AraratQuit` はどこからでも呼べる。ループが近づく前の要求は、started の段階で叶う。`--ararat-check=<name>` は、`--user-data-dir` が `$TMPDIR` の下にあり `--use-mock-keychain` があるときだけ実行され、そうでなければ 2 で終わる。`started` は 1 行の JSON `{"check":"started","ok":true,"browsers":N}` を出して終了する。`window` は非表示の host、native window、hit test を検査し、Browser の破棄を待つ。`NSApp` は Chrome の `BrowserCrApplication` である。Chromium の起動前に `NSApp` に触れる処理は存在せず、AppKit の UI は Chromium の起動時のコールバックから生成する（我々の規則）。
- Chrome の `AppController` を application delegate として維持し、終了、ログアウト、ダウンロードの確認、ウィンドウがないときの keep-alive を任せる。独自レイヤーは Dock からの再オープンと Dock メニュー、および Browser がないときにダウンロードの待機を選んだ場合を処理する。`AraratMain` は Chrome を呼ぶ前に `--no-startup-window` を追加し、再オープンはアプリの callback が処理する。通常プロファイルの openURLs、Handoff、コマンドラインの URL はキーウィンドウの Today に行を作り、最後の行を選ぶ。off-the-record の URL はページだけの host で開く。`open -a` とそのほかの Launch Services は `application:openURLs:` を通るので対象である。URL 引数つきの別の起動は、`--no-startup-window` が設定されたままで ProcessSingleton を経由し、その URL は捨てられる（未確認）。これは U10 ではなく、phase 5 の既定ハンドラの仕事と一緒に扱う。外部リンクの Air Traffic Control も phase 5 で扱う。起動時、最初のウィンドウは、保存されている `Window` レコードのうち最も新しいものを採用し、そのレコードが記録していた表示中の space を戻し、検証した選択中のタブを開く。保存されているものが無いときだけ、UUID で新しいレコードを作る。再オープンは、開いているウィンドウが使っていない保存レコードのうち最も新しいものを採用し、無ければ UUID で新しいレコードを作る。レコードは、書かれるたびに時刻を記録し（表示中 space の変更、選択、生成）、この時刻が採用の順序を決める。複数のウィンドウの保存レコードは、その復元とともに phase 5 の仕事として残る。ユーザーが閉じたウィンドウはその `Window` レコードを削除し、終了はすべての `Window` レコードを残す（unit 46 の行の規則と同じで、id は再利用しない）。終了とウィンドウの close は workspace のタブの行を変更せず、close をキャンセルすると host と Browser が残る（我々の規則）。

### 4.6 ウィンドウ、タブ、および Chrome の UI から引き継ぐ責務

host は表示したプロファイルごとに Browser と profile keep-alive を保持する。strip はすべての Browser のタブと各タブのプロファイルを含み、active id は表示中の Browser に属する。`showProfile` delegate はそのウィンドウで最後に表示した当該プロファイルの space に切り替え、host はページと Chrome のアクティブ状態を切り替える（我々の規則）。

**ウィンドウとプロファイル。**

- アプリのウィンドウ 1 つは、Views を基盤とする `NSWindow`（`NativeWidgetMacNSWindow`）1 つである。これにより、Chrome の bubble、ダイアログ、メニュー、autofill のドロップダウンが子ウィンドウとしてこのウィンドウに付随する。
- ウィンドウはタイトル付きで、close、最小化、リサイズができ、content は全体に広がる。タイトルバーは透明で、タイトルは表示しない。サイドバーにボタンを置き、AppKit 自身のボタンはフルスクリーン以外では隠す（我々の規則）。
- ウィンドウに表示する各プロファイルは、それぞれ専用の Chrome の `Browser` を持つ。その `BrowserWindow` は独自のオブジェクトであり、`BrowserView`、フレーム、タブストリップ、ツールバーを持たない。
- 拡張からは、プロファイルごとの `Browser` が別のウィンドウ id に見える。キーウィンドウに表示された Browser がアクティブとなり、ほかのアプリウィンドウの表示中 Browser はフォーカスされず、最小化もされない。非表示の Browser は非アクティブ、不可視、最小化されていない状態と host ウィンドウの bounds を報告する。アプリを非アクティブにすると、すべての Browser のフォーカスが外れる。拡張自身のコンテキストの `currentWindow` はそのコンテキストが属する Browser であり、バックグラウンドではフォーカス中の Browser、アプリが非アクティブな間は最後にフォーカスされた Browser である。非表示プロファイルへの `windows.update({focused: true})` は、そのウィンドウで最後に表示した当該プロファイルの space に切り替える。Arc の拡張から同一プロファイルの全タブが見えるか、現在の space のタブだけが見えるかは未確認である（我々の規則）。
- アプリが非アクティブになると、`windows.onFocusChanged` は `WINDOW_ID_NONE` を通知する。ウィンドウが再びキーになると、その Browser のウィンドウ id を通知する。Ararat のウィンドウ間の切り替え自体ではアプリの非アクティブ化を通知しない。別プロファイルのウィンドウへの切り替えでは、直前のプロファイルの拡張に `WINDOW_ID_NONE` を通知する（Chrome と同じ）。プロファイルと incognito の可視性には Chromium の規則を適用する（我々の規則。エンジンでの検証は未了）。
- 拡張のポップアップウィンドウ（`windows.create({type: "popup"})`）は実際のポップアップウィンドウのままとする（Cra ledger 10）。独自の内部用ヘルパーウィンドウは拡張から隠す（Ardia ledger 1.7）。プロファイルの `Browser` は内部用ではなく、拡張から見える。

現在の `AraratBrowserWindow` は表示、アクティベーション、bounds、タイトル、native window の操作を host Widget に委ね、close は Chromium の unload controller に渡す。toolbar、location bar など未実装の UI の処理は空の結果を返すか、何もしない。タブモーダルダイアログは page card の host を使う（我々の規則）。`ARWindowHost` は受け取った `NSView` を `NativeViewHost` に配置し、アプリは Browser の破棄まで host を保持する（我々の規則）。

**タブ。**

- C1 では、選択中のタブ、または split の表示対象の全タブの `WebContentsViewCocoa` を page card に配置する。それ以外のビューはツリーから外し、対応する `WebContents` を hidden にする。最後のタブを閉じると Browser は破棄されるが host は残り、次の open で同じ epoch の Browser を作る（我々の規則）。

- タブの `WebContentsViewCocoa` をどの compositor（描画の合成を担う機構）が所有するか（タブのビューごと、プロファイルごと、ウィンドウごとの共有）は spike で決定する。Ardia は、ビューごとの compositor がタブの切り替えのたびに 1〜2 回のリフレッシュ分の遅延を生むこと、および後から変更すると描画の書き直しを要することを見出したためである（Ardia ledger 1.3、1.6）。spike では、各候補について、切り替え時の最初のフレームまでの遅延、バックグラウンドのページの活動、オクルージョン、リサイズ、分割ペイン、ディスプレイの変更を計測する。
  `--ararat-compositor=c1`（既定）では表示対象のタブビューを page card に置く。`--ararat-compositor=c2` ではウィンドウの Views compositor に置き、page card の位置に合わせる。
  C2 ではページのレイヤーがアプリの NSView ツリーの下に置かれ、アプリのビューが透明な場所にだけページが見えるため、画面上の最初の確認ではページが見えるかどうかを確かめる。
  `--ararat-measure=switch|background|occlusion|resize|display|split` は、表示したウィンドウで各場面を 10 回実行し、1 回ごとに JSON を 1 行出力する。

  2026-11-07 に official のビルド（out/Ararat、157.0.8103.39）で計測した。機体は Mac Studio、ディスプレイは 1 台（3440×1440、165 Hz。1 回のリフレッシュは 6.1 ms。条件の 120 Hz のリフレッシュは 8.3 ms）である。各場面の実行の中央値と最悪値を示す。

- 新しいコンテンツ: renderer が生成したウィンドウは、既存の `WebContents` と保留中のナビゲーションの状態を保持したまま、`AddNewContents` を経由して独自レイヤーに届く。修飾キー付きのクリックやフォームの target は別の経路（`OpenURLFromTab`）を通る場合がある。常時有効な Browser コンストラクタの hook は、通常ウィンドウと popup を独自 host に渡す。host は表示中の space が名指す profile（`Space.profile`）で開き、開いている profile の通常 Browser と popup を受け取る。off-the-record はページだけの専用 host に渡す。Runtime がないとき（`started` の前、起動に失敗した後、`will_shut_down` の後）は factory は nullptr を返す。Browser は標準のウィンドウを受け取り数えられ、検査の実行のときは `ararat-trace:` を 1 行 stderr に出す。その他は下表のとおり標準のままにする。POST の target、ブロックされた popup、残りの経路は個別の検査が必要である（我々の規則）。
- 1 つの live ページは 1 か所にだけ表示する。別のウィンドウが選択すると、同じ profile の `TabModel` を移し、元のペインに短時間保持する snapshot、または中立色のプレースホルダーを表示する。ウィンドウが key になると選択中のページを取り戻す。handoff の途中で失敗した場合は close を中止して移動元を開いたままにし、すでに移動したページは移動先に残す。閉じるウィンドウのページを別のウィンドウが表示している場合は、close 確認後に移す。移動元と移動先の strip はまとめて報告し、移動途中の一時的な消失を close として扱わない（我々の規則。native 検証は未実施）。

**セッション。** 独自の `Browser` では Chrome のウィンドウの自動復元を無効にする。パッチは factory hook が設定されたすべての Browser で復元を無効にする。プロファイルを host が保持している間、独自レイヤーは起動設定を Chrome のデフォルトに固定し、変更されても戻す。これにより Browser を指定しない復元要求でも Chrome のセッションを開かない。Chrome の強制管理ポリシーはこの設定より優先される。U17b の履歴永続化は実装中であり、未検証である。その履歴ファイルはプロファイルとコアの項目 id をキーとし、close、archive、delete で削除を予約する。unload では保持する。復元にはファイルの URL と行の URL の一致を要求するため、移動した pinned 行は保存済み URL を新たに読み込む。sessionStorage は復元しない。PageState の復元はベストエフォートである。renderer からの更新は遅れる場合があり、Chromium は状態の一部を除去または無害化する（我々の規則）。

クラッシュした通常プロファイルでは、エンジンは `AraratFinishCrashRecovery` まで Chromium の `CrashedLock` を保持する。復旧前にプロファイルが破棄される場合は、クラッシュを確認済みにせず lock を放棄する。明示的な削除では要求時と通知時の 2 回無効化するため、その間に結び付いた writer は停止される。dispatch 済みの復元が取り消され、その後に transaction が適用されず終了した場合、確認は保留され、次の起動でもクラッシュが報告されることがある。これらは未検証である（我々の規則）。

### 4.7 ビルドと成果物の同一性

- ビルドはリポジトリ外に置き、通常は `~/chromium-build` を使う。通常の作業中はインクリメンタルビルドのみを行う。
- Ardia の数値: M5 Pro で初回ビルドに約 2〜2.5 時間、インクリメンタルビルドに約 7 分（コンパイルと ThinLTO の再リンク）、ディスクは約 45 GB。こちらの数値（2026-11-04、Mac Studio M3 Ultra、28 コア。素の Chromium 157.0.8103.39 の Release で `symbol_level=0` とプロプライエタリのコーデックを有効にし、ThinLTO と PGO は使わない。テストの席と CPU を分け合っていた）: 浅いソースの取得に 9.5 分、依存の取得に約 9 分（gclient の既定の並列数では googlesource が 429 を返し、`-j 4` で通った）、初回ビルドに 1 時間 16 分（57,508 手順）、`chrome/browser/ui/browser.cc` を変えた後のインクリメンタルビルドに 36 秒、ディスクは 39 GB。エンジンのビルドは nix の devshell の外で行う。devshell の `MACOSX_DEPLOYMENT_TARGET` が Chromium の rustc に渡り、ビルド用のツールのリンクを壊すからである。
- phase 2 の正式なビルド（2026-11-05、同じ機体。`engine/args.gn` は official、ThinLTO、`chrome_pgo_phase=0`、Xcode 27.2、series は 27 件）: 156.0.8078.79 の初回のフルビルドは、リンクエラーで止まるまでに 1 時間 31 分（56,691 手順）であった。series にパッチを 1 本足すと、当たっているファイルをすべて戻して書き直すため、再ビルドに 3,343 秒（50,522 手順）かかった。`chrome/browser/ui/browser.cc` を変えた後のインクリメンタルビルドは 155 秒（6 手順で、ほとんどが ThinLTO の再リンク）、`out/Ararat` は 24 GB である。157.0.8103.39 のフルビルドは 4,821 秒（57,021 手順）であった。`smoke` は両方で通った。157 では、ビルド直後の初回の起動が 1 度失敗し、その後の 4 回は通った（`smoke` が終了コードと stderr を出す前の計測である）。
- phase 3 の日々の作業は out/Dev で行う。`gen --dev` が書き、`build --dev` がビルドする（我々の規則。2026-11-05 に 157 で計測）。`engine/args.gn` に `is_official_build=false`、`use_thin_lto=false`、`symbol_level=0`、`blink_symbol_level=0`、`dcheck_always_on=false`、`enable_precompiled_headers=false` を加える（このツールチェーンでは base の `precompile.h` が module interface unit としてコンパイルされて失敗するため、precompiled header を切る）。フルビルドは 8,154 手順目で 1 度中断し、再開した分が 2,673 秒（36,301 手順）であった。ディスクは 7.2 GB、変更なしのビルドは 6 秒、`chrome/browser/ui/browser.cc` を変えた後は 31 秒（9 手順）である。配る版は `out/Ararat` で作る。こちらの層をリンクした後（2026-11-05）: 層を加えた後の最初の `build --dev` は 205 秒（1,374 手順）、変更なしの `build --dev` は 6 秒であった。`engine/ararat/` の 1 行を変えると、`apply` に 28 秒、`gen --dev` に 3 秒、`build --dev` に 28 秒（5 手順）かかる。
- ビルドが使う CPU は 95 % までとし、ビルド中も機体を使えるようにする（owner の規則、2026-11-05）。siso は `-j` を受け付けないので、`build` は `hw.ncpu` の 95 % を切り捨てた数（28 のうち 26）を `-local_jobs` で渡す。
- エンジンのビルドは共有ロックのもとで一度に 1 つだけ実行する。ロックの既定値は `<build root>/.engine.lock` であり、複数の root では `ARARAT_ENGINE_LOCK` で同じ場所を指定する。mkdir(2) ロックで、持ち主の pid を `pid` ファイルに置き、exit と INT/TERM で外す。`fetch`、`apply`、`gen`、`build` が取り、取れないときは断る。pid が空または読めないロックは奪わずに断り、エンジンコマンドが動いていないのを確かめてから `rmdir "$ARARAT_ENGINE_LOCK"` で手で外す。持ち主が死んでいるロックはアトミックに奪い直す。手でロックを持ちたいときは、ディレクトリを作って `pid` に生きている pid を書く（我々の規則）。
- エンジンの環境は `engine/scripts/env.sh` が整える: `MACOSX_DEPLOYMENT_TARGET` と `SDKROOT` を外し、`DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` を置き、`DEPOT_TOOLS_UPDATE=0` を置き、PATH を depot_tools と `/usr/bin:/bin:/usr/sbin:/sbin` に限定する。`/nix` からも呼び出し元の PATH からも何も流さない。nix の xcbuild の `xcrun` は MobileAsset の Metal ツールチェーンを見つけられず、引き継いだ PATH のままでは ANGLE のシェーダーのアクションが "missing Metal Toolchain" で失敗するからである。gclient は `-j 4`（既定の並列数では googlesource が 429 を返す）（我々の規則）。
- `fetch` は shallow にタグを取得して `gclient sync -D --no-history --shallow -j 4 --force` を行い、工程ごとに所要時間を出力する。
- `gen` は `engine/args.gn`（ハッシュを `engine/build-inputs.toml` の記録と照合する）を `out/Ararat/args.gn` に書き、`ararat_engine_version` のスタンプ（ビルドした Chromium のバージョンと、series・パッチ・レイヤーを合わせたマニフェストのハッシュ）を付け加え、`gn gen` を実行する。すべてエンジンのロックのもとで行う（ビルド中に args を書き換えたり `gn gen` を実行したりすると、実行中のビルドの下で ninja が再生成を行う）。スタンプはレイヤーの編集のたびに変わるので、レイヤーの編集は配布用の args を変え、次の `out/Ararat` のビルドは再生成と再リンクを行う。args.gn のスタンプがツリーより古いとき、`build` は「`gen` を実行せよ」と言って止まる（我々の規則）。
- `build` はまず読み取り専用の series-check を実行し、ツリーが記録されたバイトを再現しなければ、ツリーに触れずに「`apply` を実行せよ」と言って止まる（リセットも再適用もしない）。通ればロックを取り、`autoninja -C out/Ararat chrome` を上の CPU の上限のもとで行い、所要時間と手順数を出力し、`~/chromium-build/build-times.jsonl` に 1 行の JSON 記録を書く。
- `smoke` はビルドしたアプリを、`$TMPDIR` の使い捨て profile と `--use-mock-keychain` で `--headless=new --dump-dom`（data: URL）と `--version` の 2 回で実行する。どちらかでも失敗すれば 0 以外で終わる。実の login keychain を使うと、out/Dev のビルドは DOM を出した後に「Teardown watchdog expired」で終了コード 2 になり、keychain に「Chromium Safe Storage」の項目が作られる（我々の規則）。
- GN args は 1 つのファイルに置く: official build、ThinLTO、PGO、DCHECK なし、シンボルの除去、`proprietary_codecs=true`、`ffmpeg_branding="Chrome"`、独自のブランディング。phase 2 の実装（`engine/args.gn`）は ungoogled の `flags.gn` と `flags.macos.gn` にこちらの入力 `target_cpu="arm64"` を加えた形で、`chrome_pgo_phase` は暫定で 0 とし、独占の API キーは設定しない。ブランディングは phase 3 に回す。
- `engine/build-inputs.toml` は、バイナリを決定するすべての要素を固定する: Chromium のコミット、ベースのパッチセットのタグ、解決済みの DEPS のハッシュ、GN args、Xcode と SDK のバージョン、アーキテクチャ。エンジンの成果物のキーは、このマニフェストのハッシュと `engine/` の git tree である。公開する成果物には SHA-256 と provenance の記録を付ける。
- CI ではエンジンをビルドしない。エンジンはローカルでビルドし、このキーのもとで prerelease として公開する。
- 各リリースの Corresponding Source（GPL が定める対応ソース）は、タグ、`build-inputs.toml`、パッチの series、および固定した upstream を取得してツリーを再現するスクリプトである。

- U19 の 157.0.8103.39 から 158.0.8127.18 への練習リベース（2026-11-10、第 2 の root）: `out` を除く `src` のクローンに 221 秒かかり、論理サイズ約 50 GB に対して空き容量は 0.84 GB 減った。APFS は extent を共有したが、ツールでは clone と copyfile の fallback を区別できなかった。タグの取得に 328 秒、`gclient sync` に 526 秒かかった。順次適用では series 42 件中 8 件（generic 5 件、我々のパッチ 3 件）が失敗した。dry run の予測は 6 件で、`viewless-bubble-anchor` と `sad-tab-viewless` は予測できなかった。`add-credits` は残存ファイルだけが原因で失敗した。ungoogled の 158 リリースがなかったため、generic 5 件は手作業で移植しており、upstream とバイト単位では一致しない。
- 最初の移植ではその 8 パッチと `WindowOpenDisposition` の 9 箇所を修正した。その後の各回で ScreenAI の text detection に関する GN assertion、ホストの Metal toolchain（`TOOLCHAINS`）、PDF searchify の WebUI lint、`IDS_PDF_SEARCHIFY_IN_PROGRESS` のコンパイルエラー、captions の speech model installer のコンパイルエラー、`TearDownPreBrowserWindowDestruction()` の呼び出しによる Browser 破棄時のクラッシュを修正した。パッチごとの時間は記録していない。新規の `out/Dev` のビルド時間は中断を挟んだ各回の合計 440 + 2,248 + 395 + 650 + 31 = 3,764 秒であり、連続したフルビルドの時間ではない。上記の 157 の比較値も中断を含む。`out/Dev` は 7.4 GiB。`smoke --dev` の dump-dom は成功し、Chromium 158.0.8127.18 を報告した。再起動した `ararat-test` VM では U16 の 63 ケースが rater を通過し、22 件の終了検査、split、transfer、transfer-ext、screen-links、screen-profiles が終了コード 0 で通った。screen-quit と screen-prompts は 157 main と同様に失敗した。取得開始から最後の検査までは他の作業単位の待ち時間を含め約 2 時間 36 分、root・sync・ビルドによる空き容量の減少は 164 GB から 139 GB であった。

### 4.8 初日からのセキュリティとデータの完全性

- Safe Storage のキーチェーン項目の名前は最初のビルドで確定し、以後変更しない。鍵を暗黙に再生成することはしない。新しいプロファイルであることが証明できる場合にだけ生成し、それ以外の場合は再試行したうえで fail closed とする（Ardia ledger 1.8）。
- 復号したパスワードは、エンジンとコアの両方で、解放の前にゼロで上書きする。
- 子プロセスは macOS のサンドボックス内で実行する。
- アプリのバンドルには何も書き込まない。リリースの検査では、起動後に署名を再検証する。
- テスト用の自動操作のチャネルは Web ページから到達できないようにし、テスト専用のスイッチは、配布用でないビルドで、かつスクラッチのデータディレクトリを用いる場合にだけ機能する（Cra ledger 33、Ardia ledger 1.8）。
- WebRTC はローカル IP を公開しない: mDNS を無効にし、`default_public_interface_only` とする（Cra ledger 27）。

### 4.9 セキュリティの保守

- 日次のジョブが、Chromium の新しい stable リリースと、ベースのパッチセットの新しいタグを検出する（Cra ledger 6）。
- パッチの遅延の上限は、upstream の stable リリースの時点から数える。実際に悪用されている脆弱性の修正は 48 時間以内に出荷し、それ以外の High と Critical の修正は 7 日以内に出荷する。
- 同じ Chromium の milestone 上でのセキュリティ修正のみの再ビルドはインクリメンタルとし、事前に承認済みとする。milestone の更新にはフルビルドが必要であり、それを事前承認とするかはオーナーの判断である（14）。
- ベースのパッチセットが上限を超えて Chromium から遅れた場合は、自らより新しい Chromium にリベースし、ベースのパッチを引き継ぐ。
- リベースは第 2 の build root で行う。`out` を除いて `src` をクローンし、gclient の状態をコピーし、既存の root と depot_tools およびエンジンのロックを共有する。パッチの manifest を分離するため、Ararat の別ブランチを使う。第 2 の root でビルドと検査を行い、固定する版はオーナーが決める。練習を破棄するときは、オーナーの承認を得て第 2 の root とブランチを削除する（我々の規則）。次のリベースでは、手作業で移植した `disable-google-host-detection` の差異を確認する。新しい suggestion URL getter は対応するコマンドラインスイッチを渡すと有効のままである。M162 では `sad_tab_controller` と `bubble_anchor_util_views` の CHECK が fatal になるため、sad tab のガードを維持し、bubble anchor の不変条件を確認する。
- オーナーを含め、誰かが日常的に使用するには、次の 2 点が必要である: 機能する更新の経路（Sparkle）と、URL とダウンロードの評判の検査（Safe Browsing、または選定した同等のもの、14）。

## 5. 状態の所有

workspace の store は、指定時は `--ararat-db=<path>`、それ以外はエンジンから取得した Chrome の user data directory 内の `Ararat/workspace.sqlite` に置く。store の呼び出しは単一の serial queue、エンジンの呼び出しはメインスレッドで行う（我々の規則）。

### 5.1 誰が何を書くか

| 事実 | 所有者 | 備考 |
|---|---|---|
| space、ピン留め / Today への所属、favorites、フォルダ、split の項目、archive、ウィンドウごとの表示状態、Air Traffic Control の規則、キーバインド | Rust のコア | Arc のモデルの形（components note 3） |
| どの `WebContents` が、どの `Browser` に存在するか、順序、active タブ | Chrome の `TabStripModel` | Chrome がコミットする。拡張の API は同じ呼び出しの中で結果を読み戻すため、事前にアプリへ問い合わせることはしない（Ardia ledger 1.4） |
| ナビゲーションスタック | エンジンのセッションの永続化（4.6） | プロファイルとコアの項目 id をキーとする。sessionStorage は復元しない |
| 履歴、ブックマーク、favicon、閉じたタブ、ズーム、ダウンロード、パスワード、autofill | Chrome のサービス | コアには複製しない |

- 読み込まれていない workspace のタブは `WebContents` を持たない。
- コアの coordinator は id を付けて live タブのコマンドを発行する。エンジンはトランザクション `{epoch, rev, cause, strips}` で応答する。`epoch` はエンジンの起動時に変わる。`rev` は 1 つの epoch の中で単調に増加する。`cause` は、独自のコマンドの id、独自のエンジン呼び出し、Chrome 自身のいずれかである。1 つのトランザクションに複数の cause を混在させない。エコーを抑制する時間窓や、「自分が起こした変更か」を示すフラグは設けない。コマンドは、発行されてから、その id を名指すトランザクションが届くまで飛行中にあり、飛行中のコマンドは新しい epoch の始まりで消去され、飛行中のコマンドを名指さない完了は落とす（我々の規則）。
- Chrome が自ら行う変更（拡張によるタブの移動、クローズ後の後継タブ）は差分を取り、コアの規則によって workspace に適用する。後継タブは、Chrome の選択ではなくコアの規則（split の連続性、閉じたフォルダの中のタブと読み込まれていないタブのスキップ。畳んだピン留めの区画は数えないので、その中のピン留めも後継になり、そのときは holder の規則がそのピン留めを表示し続ける）に従う。後継は、Arc と同じく、そのウィンドウで表示している space のタブのうち、最も最近に選んだもので、まだ開いていて表示されているものとする（閉じる操作でサイドバーを別の space へ移さない。Arc で計測した）（2026-11-01 に ⌘W と AppleScript で計測した。閉じると選択の履歴をさかのぼり、隣のタブには移らなかった。`docs/research/arc-ardia-observed.ja.md` の 7 節）。該当するタブが無ければ、同じ一覧で閉じたタブより下にある最も近い表示中の開いたタブ、無ければ上、それも無ければ何も選ばない（我々の規則）。split の選択は member を正とし、表示は最も外側の split を用いる。現在の core はウィンドウごとに 1 つの選択を split の行に持ち、member は Chrome で active なものである（§4.6）。split 行を閉じると、その member をまとめて閉じる。pinned のタブと favorites で ⌘W を押すと、そのタブを読み込んでいない状態にし、行は残し、同じ規則で後継へ移る。選択の履歴はウィンドウごとにローカルに持ち、同期しない。
- トランザクションの strips は、運ぶウィンドウを名指し、coordinator の gone パスはそのウィンドウだけを見る。トランザクションが名指さないウィンドウから消えたタブはそのままにする（我々の規則）。閉じたウィンドウは空の strip として届くので、そのタブは消えたものとして見える。
- 採用したタブは、そのウィンドウで最後に表示した当該プロファイルの space の Today の末尾に置く。リンクから開いたタブの Arc での位置は未確認である。active な採用タブは選択するが、epoch の初回 snapshot より後の Engine による strip では選択しない。background のタブには選択時刻と後継の履歴を付けない。コアは報告された URL とページタイトルを保存し、ユーザーが付けたタイトルを保持する。ただし URL とタイトルが動くのは Today の行だけである。pinned と favorite の行は保存した URL とタイトルを保つ。Arc が pinned タブの URL を保つのと同じで、「pinned URL へ戻る」は後の unit の仕事である。opener の ID は strip で運ぶが、配置にはまだ使わない（我々の規則）。
- epoch の初回 snapshot の後は、コマンドの確認と Chrome による変更の strip がウィンドウごとの選択を更新する。Engine による strip はタブの状態と metadata を更新し、選択は変えない。プロファイル切り替え時には、要求したタブの activation より先に、その Browser で以前 active だったタブが報告されることがあるためである。Chrome による close でウィンドウの選択が変わったときは、そのウィンドウの strips の active タブは記録せず、規則が選んだ後継を残す（我々の規則）。コマンドによる strip と Chrome による strip の active タブが、そのウィンドウが今表示している space に属さないときも、そのタブは記録しない。ただし live の対応と metadata の効果は残す。space を切り替える前にした選択が切り替えの後に届くことがあり、それを記録すると表示していない space のタブを選んでページが空になるためである。このときコーディネータは、そのウィンドウが選んでいる行を、後継の再 activation と同じ形でもう一度 activate する。ページは Chrome の active タブに従うので、そうしないと表示中の space のサイドバーの下に、ウィンドウが離れた space のページが出るためである。その activation に答える strip は表示中の space のタブを名指すので、何も記録せず、次のコマンドも要求しない（我々の規則）。
- タブの切り替えでは、まずネイティブにページを表示する。表示の経路に UI の状態を経由する往復は含めない。
- Air Traffic Control は規則自身のプロファイルの内側に保つ: 規則は、その routing ファイルの持ち主のプロファイル（呼び出し側が渡す。持ち主を知らないときは、space を名指す行き先はその space のプロファイルを、それ以外の行き先は最初の space のプロファイルを、規則ごとに載せる）に属し、space の行き先はそのプロファイルの space でなければならず、Little window の行き先は workspace が持つプロファイル（組み込みのもの、または帳簿に載っている名前のあるもの）を名指しし、これらを破る編集は断られ、取り込みはその規則を飛ばす。space を消された規則はそれでも当てはまり、まず自分のプロファイルの、最も最近使われた space —— 選択の記録の中で最も新しいタブが順位をつける —— に続き、既定の行き先、既定のプロファイルの最も最近使われた space の順で答え、それも無ければ最も最近の space に送る（我々の規則）。

### 5.2 クラッシュ時の一貫性

- live タブの同一性と live id の対応は再起動後に残らない。Chrome のセッション復元は無効であり、エンジンの最初の空のスナップショットは、存在しない行を未読み込みにする。最初のウィンドウは最新の保存済み Window を引き継ぎ、検証した選択中のタブを項目 id と保存済み URL で開く。選択が split に属する場合は、focused member と他の表示対象 member を開く。他の行は未読み込みのままである。選択がない、閉じた、アーカイブ済み、表示中の space に属さない、祖先か URL が無効、または Open が失敗・取消された場合はカードを空にする。Arc の再起動時の動作は未計測である（我々の規則）。
- 起動時、エンジンは新しい epoch の完全なスナップショットを報告し、coordinator はそれを workspace と照合する。workspace を正とし、各項目のライフサイクル状態を変更と同じトランザクションで記録する。閉じる操作とアーカイブは、coordinator がエンジンに伝える前に commit する。項目が閉じた、アーカイブした、または削除した状態のエンジンのタブは、取り込まずに閉じ直す。epoch の途中で項目なしで届いたタブ（⌘ クリック、`window.open`）は、そのウィンドウで最後に表示した当該プロファイルの space の Today に取り込む。URL は commit 済みのナビゲーションが報告されるまで空とする。採用した live タブと項目の対応は WebContents の user data に保持する。エンジンが live と報告した未読み込みの行は open に変わる（我々の規則）。
- 落とされたトランザクションは rev を消費する。同じ rev の後のトランザクションは、再送ではなくエンジンのバグである（我々の規則）。
- コマンドの完了は発行時の epoch を持ち、現在の epoch でなければ捨てる。
- クラッシュの確認には `CrashedLock` と `AraratFinishCrashRecovery` を使う。復旧前にプロファイルが破棄された場合は、確認済みにせず lock を放棄する（4.6）。確認は crash の check で検査し、放棄の経路は native では検査していない。
- クラッシュ時に失われうる範囲: workspace の変更は SQLite トランザクションのコミット時に永続化される。大半の編集は成功を返す前に flush するが、選択と space の変更は 1 秒ごとのバッチを待つ。live の照合は flush が失敗した場合もメモリ上の結果と永続化エラーを返し、書き込みを再試行する。書き込みが失敗すると、再試行が成功するまで失われうる範囲が広がる。workspace の変更と送信用の同期ログは同じトランザクションで書く。
- ディスクの容量不足や書き込みの失敗の場合は、メモリ上の状態を保持し、バックオフ付きで再試行し、ユーザーに通知する。データベースを切り詰めることはしない。
- close、archive、delete（archive の項目、folder、space）は workspace の変更とともに、ローカルの永続的な履歴削除 outbox を記録する。unload では記録しない。U17b は consumer と admission stamp を追加し、古い purge が新しい writer のファイルを消さないようにする。エンジンとの接続は history-purge の check で native に検査する。復元にはファイルの URL と行の URL の一致を要求する。
- 明示的な履歴削除ではプロファイルの generation を無効化し、既存の writer を停止する。自動的な期限切れは対象外とする。marker とファイルの削除は履歴用シーケンスで行う。marker の永続化前のクラッシュや削除失敗では古いファイルが残ることがある。通常のファイル削除であり、復元不能な消去は保証しない。失敗はログに記録して再試行し、ユーザーへの表示は phase 4 に残す（未検証）。
- バックアップには SQLite の backup API を用いるため、WAL も含まれる。

### 5.3 プライベートブラウジング

phase 4 の目標: off-the-record のプロファイルは、エンジンの契約における属性であり、すべてのトランザクションとタブがこの属性を持つ。コアは off-the-record の workspace の状態をメモリ上にだけ保持し、それに対する永続的な書き込み、archive のエントリ、同期のレコード、command bar の学習を 1 か所でまとめて拒否する。テストでは、プライベートタブを開いた状態でのクローズ、クラッシュ、archive、同期を対象とする。

U26f の pass 1・2 で実装した: エンジンはすべてのトランザクションとタブに `Browser::GetProfile()->IsOffTheRecord()` から `off_the_record` を付け、コアはこの属性が無いか、タブと食い違うトランザクションを、workspace を変更する前に拒否する。プライベートの workspace は store を持たないメモリ上の別の workspace であり、変更の前に 1 つの受け入れの規則を通す。この規則は、タブ、選択、live の状態、Today の中の並べ替えを許し、閉じる、archive、Clear を削除として扱い（archive のエントリ、Undo、最近の利用の記録、履歴の削除の outbox は作らない）、取り込み、設定、routing、2 つ目以降の space、フォルダ、ピン留め、favourites、復元、別の workspace からの移動を拒否する。U26f の pass 3・4 で実装した: off-the-record の通常 Browser は完全なウィンドウの host である。同じ off-the-record の `Profile*` のウィンドウは、最後のウィンドウを閉じるまで 1 つのプライベート workspace を共有し、正常な終了の後もクラッシュの後も復元しない。strip は同じ `Profile*` の host にだけ届くので、プライベートの strip が通常の store に届くことはない。space は Today だけの 1 つであり、command bar は何も学習せず、履歴を出さない。プライベートと通常のウィンドウは互いの workspace を見ない。同じ off-the-record プロファイルの host の間の移動は許し、プロファイルをまたぐ移動は拒否する。プライベートウィンドウが active の無い最初のタブを取り込んだとき（何も選ばれていない間はページを隠すため）、コアはそのタブをウィンドウの記録の中でだけ選択する。プライベートウィンドウは最後のタブを閉じると閉じる。Clear はタブを削除し、トーストも Undo も出さない。プライベートウィンドウのダウンロードは確認なしに通常のダウンロードフォルダに保存し、その一覧は最後のウィンドウを閉じたときに解放する。ウィンドウは常にダーク（sidebar を含めて `darkAqua`）であり、URL 欄と空のページに仮面のマスクと「Private」を出す。これを `private-window`、`private-isolation`、`private-downloads`、`private-durability` のチェックで確かめる。最後のチェックは正常な終了と kill の後に起動し直し、`workspace.sqlite`、その WAL、プロファイルのファイルのどこにもプライベートのタイトルと URL が無いことを確かめる。Arc のプライベートウィンドウは未確認である（我々の規則）。

## 6. Rust のコア

### 6.1 内容

- workspace のモデル: プロファイル、space、コンテナ（favorites はプロファイルごと、または space ごと、14）、項目（タブ、フォルダ、split）、archive のエントリ、ウィンドウの状態。
- ツリーの表現: 各項目は所属のレジスタ `(parent id, fractional order key, HLC, previous parent id)` を 1 つだけ持つ。子のリストは導出するものであり、別に保存しない。修復は、merge したレジスタの上の決定的なビューである。修復の結果は、同期するレジスタに書き戻さない。そのため、同じ移動を異なる順序で受け取ったデバイスも、同じツリーを計算する。修復したレジスタを書くのはインポートだけである。インポートするファイルがそれらのレジスタの出どころだからである。決定的な修復は次のとおりである。循環を生む移動は、HLC（ハイブリッド論理時計）のタイムスタンプが大きいほうの移動を残し、もう一方の項目を以前の親に付け直して解決する。親が存在しない項目は、その space の Today コンテナに移す。space は移動前の親（レジスタに記録する。新しく作った項目、たとえば新しいフォルダや複製の根は、ここに一覧の根を記録するので、親が並行して削除されても別のプロファイルへ移らない）の祖先のコンテナから決め、決まらなければ先頭の space とする。以前の親に戻しても循環が解けない項目は Today に移す。削除と並行する編集とでは、編集が復元である場合を除き、削除を優先する。ツリーの不変条件のテスト（循環がないこと、すべての項目にちょうど 1 回到達できること）と配送順序のテストは、すべての merge のテストで実行する。
- 項目の編集: 移動はコンテナと位置で指定し、並べ替え、ピン留めとその解除（Today ↔ ピン留め）、任意の深さのフォルダへの出し入れ、お気に入りへの出し入れ、別の space のピン留めや Today への移動を扱う。core はフォルダを中身ごと移動するが、サイドバーではフォルダのドラッグを開始しない。自分の中への移動は断る。split は 1 つにまとめて動かし、何も変わらない移動は何も書かない。フォルダはピン留めの中にだけ置き、お気に入りにはタブだけを置く（Arc、`docs/research/arc-ardia-observed.ja.md` の 8 節）。Today への移動とピン留めの解除では最後に選んだ時刻を付けるので、自動アーカイブは移動の時点から数える。タブを選ぶと、そのタブを囲む閉じたフォルダを開く。選んでいるタブは移動の後も選んだままとし、別の space への移動では表示中の space を切り替えない。同じ順序のキーの間に落としたときは、キーを付け直す。プロファイルをまたぐ移動は断る。移動先のプロファイルでの再読み込みが必要であり、phase 3 の対象外とする（我々の規則）。フォルダは指定した位置に作り、1 つの space の項目を包んで作ることもできる（並びは見た目の順。split の構成タブは繰り上げる）。名前の変更と削除もできる。空のフォルダはすぐに消し、タブの入ったフォルダは中のタブをアーカイブし（Arc、8 節）、残る項目はピン留めの直下に移す。タブの名前も変えられ、独自の名前をページのタイトルの代わりに表示する。空の名前にすると独自の名前を消す。複製（Duplicate）は、タブ、フォルダ、お気に入りを元の項目の直後に写し、id は core で新しく作る。写しは読み込んでいない状態で、URL と名前は元と同じとする。フォルダの写しは中の並びと開閉を保ち、中のアーカイブ済みの項目は写さない。split の構成タブを複製すると split 全体を写す（我々の規則）。写しの最後に選んだ時刻は複製した時刻とするので、古い元の項目に引かれて写しがすぐにアーカイブされることはない。選択、表示中の space、履歴は変えない（我々の規則）。
- 規則: Arc 上で計測したとおりの Air Traffic Control の照合（大文字小文字、スキーム、先頭の `www.` を無視する。「Contains」はクエリとフラグメントも検査する。「Is equal to」はホストとパスだけを比較し、末尾のスラッシュは無視する。最初に一致したものを採用する）、自動 archive の閾値、後継タブの規則、split のレイアウトの計算。アクティブなタブが切り替わると、切り替え元のタブにその時刻を記録し、自動アーカイブは最後に表示した時点から時間を数える。バックグラウンドの strip の変更や、同じアクティブタブの再報告では時刻を更新しない（我々の規則）。
- live-tab coordinator: エンジンのトランザクションを適用し、コマンドを発行し、起動時に照合する（5）。
- インポート: Arc（`StorableSidebar`、`StorableWindows`、`StorableArchiveItems`、`StorableKeyBindings`、`StorableLinkRouting`）、後に Dia、Chrome、Safari、Firefox。インポートは Arc のファイルから workspace とインポートの報告を作り、ストアが 1 回のバッチで書き込む。Chromium のデータ（パスワード、cookie、履歴）は、エンジンを介して Chrome のストアに書き込む。Arc のウィンドウの状態（Ararat の規則。ファイルの形は `docs/research/arc-dia-components.ja.md`）: サイドバーのファイルの隣の `StorableWindows.json` は無くてもよく、無い、読めない、UTF-8 でない、形が壊れている、のどの場合もサイドバーの取り込みは止めない（後の 2 つは報告する）。フォルダの状態とタブの日時は最初のウィンドウから取る。その `expandedItems` は、フォルダを `expanded`（開いている）か `peeked`（閉じたものとして取り込み、数える）で示し、載っていないフォルダは閉じる。その `itemLastActiveDates` は 2001-01-01 からの秒数で、Unix のミリ秒にして保存する。報告は、後のウィンドウと食い違うフォルダ（フォルダごとに 1 回）、peeked のフォルダ、最初のウィンドウの未知の id と形の壊れた項目（項目ごとに 1 回。1 つのウィンドウに 2 回載ったフォルダは後の組を採り、2 件になることがある）、未来の日時、タブでない項目の日時を数える。2 回日時が載ったタブは数えない。Arc のキー割り当て（我々の規則）: `StorableKeyBindings.json` は版を先に読む。`userOverrides` が空なら何も取り込まない。空でない一覧は、形を確かめた例がまだ無いので、報告で数えるだけで取り込まない。Arc の Air Traffic Control の規則（Arc の形は Cra の `Sources/Cra/Model/LinkRouting.swift:8-24` による。ほかは我々の規則）: サイドバーのファイルの隣の `StorableLinkRouting.json` は版を先に読む。`contains` は Contains、`matches` は Is equal to にする。行き先が `space` で `mostRecent` のものは最近の space、知っている space の id のものはその space にする。`littleArc` は、routing ファイルの持ち主のプロファイル（呼び出し側が渡す。知らないときは最初の space のもの）の Little window にする。プロファイルの行き先、知らない照合の種類や行き先や space の id（持ち主のプロファイルに属さない id は知らないものと同じに数える。持ち主を知らないときは、生きている space の id ならどのプロファイルでも残し、規則にはその space のプロファイル——most-recent と Little window は最初の space のもの——を載せる）、形の壊れた項目、重なった id（最初のものを残す）は、飛ばして数える。ファイルが無いときは無いと報告し、形の確認に通らないファイルは断って報告する。どちらの場合もサイドバーの取り込みは止めない。規則はファイルの順に入れ、空や空白だけの条件は何にも当てはまらない（Cra の `LinkRouting.swift:37`）。
- エンジンが供給するソース（Chromium の HistoryService の履歴、開いているタブ、workspace の項目、コマンド）に対する command bar の順位付け。エンジンの無い今の形（Cra の点数。file:line は各 unit の報告にある）: 開くたびに、workspace を修復した写しから索引を 1 つ作り、閉じると捨てる。候補は、開いているタブと読み込んでいないタブ（今のタブは除き、お気に入りには印を付ける）、コマンド（割り当てたキーを添える）、表示中以外の space への Switch to、フォルダへの Go to、Move Tab to である。Move Tab to は、同じプロファイルの別の space（その Today の末尾）か、タブが今入っているもの以外の同じプロファイルのフォルダ（そのフォルダの末尾）へ移す。URL で重複を除き、打った文字の行の後に、開いているタブ、履歴、コマンドの順にまとめる。ただし、名前が問い合わせで（語の頭から）始まるコマンドのうち最もよい 1 つは 2 行目に置く（U23、design の判断）。空の問い合わせは、表示中の space の最近のタブを 5 件まで並べる（今のタブとお気に入りは除き、読み込んでいないタブは含める）。プライベートウィンドウの問い合わせには履歴の行を出さない。スキーム、`localhost`、`about:`、`file:`、IPv4 のアドレス、host.tld[:port][/path] のどれかで空白を含まない問い合わせは URL として開く（localhost と IP は http、ほかは https）。それ以外は `https://www.google.com/search?q=` で検索する（エンジンの検索エンジンが入るまでの定数）。打った文字そのものも 1 行とし、常に先頭に置き、Return でそれを実行する。表示は 5 行までとし、コマンド、space、フォルダは 2 文字から当てはめる。履歴は HistoryService への薄い問い合わせ（URL とタイトルの一致）で取り、点数は core で付ける。入力中の補完とネットワークの検索候補は無い（Show search suggestions のスイッチは General のペインを待つ）。`create_tab` は表示中の space の Today の先頭にタブを作って選び、`set_tab_url` は開いているタブか読み込んでいないタブの URL を変え、それ以外は断る。
- 同期クライアント（8）。

### 6.2 ストレージ

workspace、archive、同期のジャーナルには SQLite（WAL）を用いる。書き込みはメインスレッド外で実行する。Cra の JSON ファイルは、書き込みをメインスレッド外に移す前、2,000 項目の archive の書き込み 1 回あたりメインスレッドで約 30 ms を要した（Cra ledger 16）。SQLite は 5.2 が必要とするトランザクションを提供する。

各レコード（space、item、favorites のコンテナ、キー割り当ての変更、プロファイルのアーカイブの閾値、Air Traffic Control の規則と既定の行き先、New Tab の行の表示などの workspace の設定）は 1 行 `(kind, id, JSON の本体)` として保存する。space も item と同じく fractional order key を持ち、一覧は保存しない。各変更は同じトランザクションでジャーナルの表にも追記する。ただし次の 6 種類は端末の中だけに置き、ジャーナルにも同期にも載せない: `Window`（ウィンドウの位置と大きさ、サイドバーの状態）、`LastSelected`（各タブを最後に選んだ時刻または切り替えた時刻。自動アーカイブが読む）、`FolderState`（閉じているフォルダ。ある Mac で閉じても別の Mac では閉じない）、`SectionState`（ピン留めの区画を畳んでいる space。同じ理由による）、`HistoryPurge` と `HistoryProfile`（履歴の削除の outbox と、各タブの履歴が属するプロファイル）。Arc のインポートは、そのバッチの中で `FolderState` と、タブに限って `LastSelected` を作る。この版が知らない kind の行は変更せずに残す（8.3）。writer スレッドは、バッチの最初の変更から 1 秒以内に `synchronous = FULL` で commit する。

### 6.3 バインディング

- `ararat-ffi` は、UniFFI（macOS と iPhone の Swift 向け）と C ABI（Windows と Linux 向けの、Chromium のツリー内の C++ 向け）を介してコアを公開する。
- コアは同期的であり、ストレージの書き込み用スレッドと同期のワーカー以外のスレッドを所有しない。Swift のアダプターは 1 つの serial queue からコアを呼び出し、スナップショットを UI に公開する。
- 秘密情報は、コアがゼロで消去するバイトバッファとして境界を越える。秘密情報を Swift の `String` に変換することはしない。

## 8. 同期

### 8.1 モデル

phase 8 では、複数の端末で同時に作成しても収束するよう、お気に入りのコンテナ ID をプロファイルから導出する。

- アカウントは存在しない。同期グループは 1 台のデバイスで作成し、256 ビットのグループ秘密を基盤とする。グループ秘密は 24 語の BIP-39 リカバリーフレーズとして表示する。
- サーバーは平文、名前、秘密情報を一切見ない。サーバーは不透明な blob を保存し、それを返すだけである。

### 8.2 プロトコルの要件

同期のコードを書く前に、バージョン付きのプロトコル仕様（`docs/sync-protocol.md`）を作成し、レビューする。プロトコルは次の要件を満たさなければならない。

- 鍵スケジュール: 現在の epoch の秘密（最初の epoch ではグループ秘密、それ以降の epoch では新しいランダムな秘密）から HKDF でコンテンツ鍵、名前鍵、リレー鍵を導出し、それぞれに別のラベルを用いる（ドメイン分離）。
- 暗号化: ランダムな 192 ビットの nonce を用いた XChaCha20-Poly1305。これにより、独立したデバイスの間で nonce を調整する必要がない。AAD は、グループ、epoch、デバイス id、シーケンス番号、オブジェクト名を束縛する。
- デバイスの識別: 各デバイスは専用の署名鍵ペアを持つ。すべての blob に署名する。デバイスは署名付きのメンバーシップのレコードに列挙する。
- ペアリング: 新しいデバイスは、リカバリーフレーズを入力するか、既存のデバイスが表示する短いコードを PAKE（たとえば CPace）に通して参加する。これにより、推測または傍受されたコードから秘密が漏れることはない。
- リレーの認可: リレーは、グループに登録されたデバイス鍵からの書き込みだけを受け付け、リレー鍵から導出したリレー用の資格情報による読み出しだけを受け付ける。リレーはコンテンツ鍵を保持しない。
- リプレイ: 各デバイスはデバイスごとのシーケンスのチェックポイントを保持し、チェックポイント以下の blob を拒否する。
- 削除: デバイスを削除すると、新しいランダムな epoch の秘密から新しい epoch を開始する。この秘密は、削除の操作をしたデバイスが残りの各デバイスの鍵で封緘して送り、group secret だけからは導かない。そのため、削除されたデバイスは新しい鍵を導けない。古い epoch の relay の credential は失効させ、membership のレコードからそのデバイスを外し、残りのデバイスは新しい epoch のもとでスナップショットを封緘し直す。削除ではグループ秘密も置き換える。オーナーには新しい recovery phrase を示し、古いフレーズではグループに参加できなくなる。フレーズでの参加には現在のグループ秘密が要るからである。各 epoch の秘密は、現在のグループ秘密から導いた復旧用の鍵で封緘して relay にも置く。そのため、残る端末が無くても、現在のフレーズだけで現在の鍵を取り戻せる。グループ秘密を先に置き換えるので、削除された端末はそれを開けない。復旧は、取り戻す対象の epoch の秘密に依らない。グループ秘密からは、別のラベルで、復旧用の読み出しの credential と、復旧用の署名鍵の対も導く。relay は、前者ではその封緘した blob だけの読み出しを受け付け、後者の公開鍵をグループについて保持する。フレーズで復旧する端末は、この credential で blob を読み、復旧用の鍵の署名を付けて自分の新しいデバイス鍵を登録する。グループ秘密を置き換えると、relay の側でも両方を置き換えるため、古いフレーズでは blob を読むことも、端末を登録することもできない。
- 最初のリリースからの復元の安全性: バックアップから復元したデバイスは新しい incarnation を得て、incarnation やシーケンス番号を再利用しない。

### 8.3 データの経路

- 各デバイスは追記だけを行う: シーケンス番号付きのデバイスごとのログと、version vector 付きの定期的なスナップショット。どのデバイスも他のデバイスの blob を書き換えない。
- merge は、ハイブリッド論理時計に基づくレコードごとの last-writer-wins とし、merge の後に 6.1 のツリーの規則を適用する。
- blob は 1 KiB 単位にパディングし、圧縮しない。
- ローカルのジャーナルは、アップロードの前に、workspace の変更と同じトランザクションで書き込む（5.2）。
- tombstone（削除を表す記録）は、デバイスの退役、epoch、長期間不在だったデバイスに対するスナップショットによる再参加の義務付けが実装されるまで無期限に保持する。これらが実装されて初めて回収を許可する（Ardia ledger 3 は、取り消した試みから判明した要件を列挙している）。
- 新しいレコードの種類は、古いバージョンが読み取らず、そのまま保持するキーのもとに追加する。これにより、古いクライアントが新しいレコードを損なった状態で書き戻すことはない。iPhone のクライアントは、使用できないレコードの種類（たとえば拡張）も保持する。

### 8.4 同期の対象

workspace、Air Traffic Control の規則、キーバインド、設定、パスワード、Web Store の拡張を同期する。Air Traffic Control の規則は workspace ごとに持つ。規則ごとに、fractional order key を持つ同期の `routing_rule` のレコードを 1 件置き、item と同じく上書きだけで merge する。既定の行き先は、変えたときだけ `routing_default` のレコードを置き、消すと既定に戻る。キー割り当ての変更はコマンドごとに全体で 1 つとし、同期する `key_binding` のレコード 1 件に置く。既定は導くもので保存しない。null はそのコマンドを無効にし、レコードを消すと既定に戻る。キーを割り当てると、同じバッチで、そのキーを持つほかのコマンドから外す。merge したレコードが 1 つのキーを複数のコマンドに与えたときは、core のコマンド表で先にあるコマンドが持ち、ほかのコマンドはキーを示さずに Conflicting とし、求めたキーは報告する。持ち主が後でキーを外す、移す、戻すと、Conflicting のコマンドは自分のキーを取り戻す。読むだけの操作は何も書かない。パスワード: エンジンはレコードをゼロで消去するバッファとしてコアに渡し、コアがそれを封緘する。平文がブラウザプロセスの外に出ることも、UI のレイヤーに届くこともない。拡張は、バージョンと権限が承認済みのものと一致する場合にだけ、別のデバイスで有効にする（Ardia ledger 1.5）。履歴の同期は後で対応する。

### 8.5 サーバー

小規模な Rust のサービスである: グループごとの blob の put/get/list、デバイス鍵の検証、レート制限、サイズの割り当て。ストレージは SQLite または S3 互換のストアとする。ホスティングはオーナーの判断である（14）。

### 8.6 採用しなかった案

- Chrome Sync: Google を必要とする。
- セルフホストの Chromium 同期サーバー（Brave の `go-sync`）: Chromium のデータ型しか扱えないため、workspace には第 2 の仕組みが必要となる。また、iPhone のアプリには Chromium の同期エンジンが存在しない。
- ユーザーが選択するフォルダ（Ardia）: iPhone と Windows に同じ方法で届くフォルダは存在しない。オーナーはサーバーを選択した。

## 9. 拡張、コンテンツブロック、DRM、Safe Browsing

- Arc の取り込み（U27j）が運ぶのは sidebar、windows、キーバインド、リンクの経路だけである。拡張、ログインの状態、パスワード、cookie、履歴は取り込まないので、「Add from Arc」は拡張の一覧とこの節の承認の規則を待つ。Settings › Extensions のペイン（U27x）は通常のプロファイル 1 つの拡張を一覧して操作するが、「Add from Arc」の区画も「Find more」の行も置かない。Arc の拡張の一覧は Arc のファイルを読み、Chrome Web Store からのインストールの道もまだ無いので、どちらも owner の Arc の確認（§14）を待つ。オンボーディングの流れは検査のデータベースで自前のストアを開く。出荷する入口では、再起動なしでブラウザのウィンドウに取り込んだ space が出るよう、動いているセッションのストアを通して取り込むこと。

- 拡張は実際の `Browser` と `TabStripModel` のオブジェクト上で動作する。このため、`chrome.tabs`、`chrome.windows`、アクションのポップアップ、サイドパネルは Chrome の実装を用いる。
- インポート: Web Store の拡張は Web Store から再インストールし（検証済みのパッケージ）、ツールバーの順序は移行元のブラウザのピン留めリストから取得する（Cra ledger 8b）。パッケージ化されていない拡張は、拡張ごとに明示的な承認を得た後にだけインポートする。Chromium の権限、ブロックリスト、シークレットの検査は変更せずに適用する。
- ネイティブメッセージング: 他のブラウザ向けに登録されたホストのマニフェストは、マニフェストと実行ファイルのコード署名を検証した後にだけ独自のプロファイルにリンクする。Chrome 自体を操作するホストはリンクしない（Cra ledger 29）。
- Web Store からのインストールと更新は Google に直接接続し、Google の拡張の kill switch は有効のままとする（Ardia ledger 1.7）。
- コンテンツブロッカー、DRM、Safe Browsing はオーナーの判断である（14）。第 2 のページエンジンを採用するとページの API が変わるため、DRM は phase 6 の API 凍結の前に決定する。

## 10. 他のプラットフォーム

- **Windows と Linux。** エンジンのツリーとレイヤーは同一である。UI は Chromium の Views（C++）で実装し、C ABI を介してコアをリンクする。coordinator、規則、同期は変更せずに再利用する。Wayland ではクライアントがグローバルなポインタの位置を読み取れないため、フローティングサイドバーのウィンドウ外の規則は Wayland では制限される。
- **iPhone。** App Store のブラウザは WebKit を使用する。例外は日本（iOS 26.2 以降）と EU（iOS 17.4 以降）であり、これらの地域では Apple のブラウザエンジンの entitlement のもとで別のエンジンを使用できる。この entitlement は、適時のセキュリティ更新を含む Apple の基準を満たすことを要求する。iPhone のアプリは、WKWebView と SwiftUI/UIKit の UI、および同一の Rust のコアと同期で構成する計画である。iPhone では Chrome 拡張は使用できない。iOS 向けの Blink のビルドは計画していない。

## 11. テストと計測

- コア: 誤っているとデータを失うか漏らすもの（merge、ツリーの不変条件、クラッシュ時の照合、インポート、ATC の照合、archive の規則）と、出荷済みのバグ（Ardia ledger 1.9）に対するユニットテスト。
- UI: harness は fixture のデータでコンポーネントを実行する。コマンドのチャネルにより、ポインタを使わずに harness を操作する。
- エンジン: 広い範囲を網羅するための非表示のインスタンスと、非表示の実行では確認できないもの（フォーカス、passkey、フルスクリーン、アクセシビリティ、compositor のタイミング）を確認するための表示ありの検査。
- クラッシュと再起動のテスト: 選んだ時点でプロセスを kill し、照合を検査する。
- 同期: 編集の後にオフラインから復帰するデバイス、デバイスの削除と鍵の更新、バックアップからの復元。
- 最初のビルドから、メインスレッドの引っかかりの監視を行う（Cra ledger 13）。
- 性能の関門: 1 つのベンチマークコントローラーが、分離した対照（前回のリリース）と候補のプロセスを、同じ fixture で交互に実行し、実時間だけでなく回数（レイアウトのパス、ストアの更新、エンジンとの往復）に上限を設ける（Ardia ledger 1.9）。
- 速度に関する変更は、所有者と削除日を定めた kill switch の背後に置いて出荷する。

## 12. 配布

- Developer ID による署名と notarization。Sparkle 2 と EdDSA 署名付きの appcast、stable と nightly のチャネル（macOS）。
- bundle id、team id、entitlement（passkey 用のキーチェーンのアクセスグループ、Bluetooth の使用）、ヘルパーの署名は、資格情報の保存がこれらに依存するため、phase 3 の spike で確定する。

- CI では署名のフェーズをビルドのフェーズから分離する。action はコミットの SHA で固定する。
- すべてのリリースに Corresponding Source を付ける（4.7）。
- Windows と Linux のアップデーターは、それぞれの phase で決定する。

各 phase は、動作するビルドとサンドイッチ型のレビューで終える。

U17a は workspace の再調整を検査する 2 回起動の `--ararat-check=relaunch|crash` と、renderer crash からの復旧を検査する `--ararat-check=sadtab` を加える。seed は各 fixture の行を workspace で選択してから開く。driver は stderr を転送し、失敗時の JSON に 1 回目の最後の trace、stderr の末尾 4 KiB、終了ステータスまたはシグナルを記録する。U17b では 2 回起動の検査に履歴の flush 成功と Back スタックの復元を追加する。native exit では relaunch は通ったが、crash は前回が正常終了だったと読み取った。その後の profile preferences の commit 完了を待つ修正は、エンジンでは未実行である（我々の規則）。

U17b は非表示の `--ararat-check=history-clear` と `--ararat-check=history-purge` を追加し、無効化、期限切れ、purge の順序、pinned の unload、ファイルの破損、削除の再試行を検査する。両方とも native exit で通った。off-the-record の writer を拒否する guard は未検証である（我々の規則）。

slice の検査は `--ararat-check=slice`、`$TMPDIR` 下の新しい `--ararat-db`、一時的な user data directory、mock keychain を使う。3 行のうち 2 行を開き、2 行目を選び直す。画面上の検査は U8 で行う（我々の規則）。

U9 の検査も一時的な profile、database、mock keychain を使う。`--ararat-check=quit` は終了前後の保存済み行を比較する。`--ararat-check=quit-cancel` は beforeunload で Stay と Leave を選ぶ。`--ararat-check=close` はウィンドウの close、再オープン、Dock メニューを検査する。`--ararat-screen=quit` はウィンドウを表示し、⌘Q と Cocoa の beforeunload ダイアログを検査する。quit の検査は、エンジンのメインループが戻った時点で Chromium 自身の teardown より前に JSON の 1 行を出力する。エンジンの終了期限を過ぎた teardown（`chrome/browser/shutdown_watchdog_mac.cc` が `RESULT_CODE_HUNG` で終了する）が結果を持ち去ることはないが、その失敗はプロセスの終了コードに残る。その時点より後に失敗した実行は 2 行目を出力するので、最後の行が有効な結果である。quit の結果は、`ok` の入力すべてを名前付きの条件として持つ（`conditions`、`failed_conditions`）。`ok` だけでは、どの条件が落ちたのか分からないためである。`--ararat-screen=quit` は offset 以降の closing all browsers の生の並び（`[true, true, false, true, true]`）を検査し、畳んだ遷移は診断として出力する。1 回の ⌘Q は `chrome::AttemptExit()` を経て `-[AppController tryToTerminateApplication]` に届くため `true` を 2 回通知し、beforeunload の Stay が `false` を 1 回加える（我々の規則）。

U10 の検査も同じ一時 profile・database・mock keychain を使う。`--ararat-check=newtab|popup|menu|deferred` は Chrome が作るタブ、popup、メニューと外部 URL、後続 unit に残す Browser の種別を検査する。`--ararat-screen=links` はウィンドウを表示し、リンクの入力と popup の配置を検査する（我々の規則）。
