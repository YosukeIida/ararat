# Ararat architecture

Status: draft 2, 2026-10-30. Japanese translation: `architecture.ja.md`. Review history: `reviews/`.

This document fixes the technology choices, the layers, what is tightly coupled and what is isolated, how state and sync work, and the roadmap. It builds on three research notes:

- `research/ardia-ledger.md`: design decisions and rewrites in Ardia (Chromium fork, React Native UI).
- `research/cra-ledger.md`: design decisions in Cra (Swift + CEF) and the CEF workarounds it needed.
- `research/arc-dia-components.md`: the component inventory, data formats and Chromium seams of Arc and Dia, collected from published reverse-engineering.

References like "Ardia ledger 1.4" point to sections of those notes.

## 1. Goal and constraints

Ararat is a browser with Arc's workflow (spaces, pinned and Today tabs, favorites, folders, archive, command bar, Little Arc, Air Traffic Control, split view) and Yab's vertical-tab behaviour, on Chromium, with Chrome extensions.

Constraints, set by the owner:

- macOS first, with a native UI in Swift.
- The engine is a Chromium fork, with our own layer inside the Chromium tree.
- Windows, Linux and iPhone come later. The structure must not need a rewrite to add them.
- The cross-platform core is Rust.
- Sync runs through our own server and never requires an account or a login.
- Licence: GPL-3.0.
- Arc and Dia are closed source; Yab is Apache-2.0 since 2026-11-14, so its code may be reused with its copyright and licence kept, the changes stated and its NOTICE carried over, but its names, logo and app icons are trademarks and its Central Icon System icons are licensed separately, so those are never copied. We use published analyses and static analysis their terms allow, and copy no other code or assets. Ardia's code (GPL-3.0) may be reused with its source noted.

## 2. Decisions at a glance

| Area | Decision | Why | Section |
|---|---|---|---|
| Engine embedding | Chromium fork with our layer `//ararat/core` linked into `//chrome:chrome_framework` (the ArcCore / ArdiaCore model). No CEF at any stage | CEF fights the window model, tab creation and the run loop; 77% of Ardia's engine patch lines existed only to pass Chrome objects through CEF (Ardia ledger 1.1). Cra needed about 30 CEF workarounds (Cra ledger 3.1) | 4 |
| Engine base | Chromium plus the ungoogled-chromium patch set (the owner's choice, 2026-11-04) | Helium builds on ungoogled-chromium and adds mostly what Ararat would skip (password manager removal, keychain renaming, Sparkle, onboarding, !bangs, the Web Store proxy); its codecs come from GN args and its packaging is replaced by ours. Ardia, after moving to Helium, carries 18 patches undoing Helium and ungoogled behaviour, and its reason for the move is not recorded (Ardia ledger 1.2) | 4.2 |
| Engine ↔ app API | A handwritten, typed Objective-C API exported from the framework, called from Swift | Swift imports Objective-C with no generated glue. Dia also exposes Objective-C to Swift, but generates its 146 classes from mojom | 4.4 |
| Run loop | Chromium owns the process and the main loop; the AppKit UI starts inside it | Removes the external-pump bugs (Ardia ledger 1.1) | 4.5 |
| Window model | One Views-backed `NSWindow` per app window, holding one Chrome `Browser` per profile shown in it. Tab views go into our view tree | Chrome's bubbles and dialogs attach to the window; profile switching is a view swap; overlays are ordinary subviews | 4.6 |
| State ownership | The Rust core owns the workspace and the live-tab coordinator; Chrome's `TabStripModel` owns live tabs; they meet through epoch-qualified, revisioned transactions | One writer per fact (Ardia ledger 1.4); the coordinator in Rust is reused on every platform | 5 |
| Core | Rust crate `ararat-core`, SQLite storage, UniFFI bindings for Swift, a C ABI for C++ | Same core on macOS, Windows, Linux and iPhone | 6 |
| macOS UI | AppKit for everything that moves and for onboarding. Settings panes use SwiftUI. | Cra measured 1900 → 440 ms main-thread time on a space swipe after moving from SwiftUI to AppKit (Cra ledger 12) | 7 |
| Sync | End-to-end encrypted, account-free; our server is a blind relay of authenticated, append-only blobs; devices join with a recovery phrase or a PAKE-authenticated pairing code | "Own server, no login"; works where no Chromium sync engine or shared folder exists (iPhone, Windows) | 8 |
| Process | Scope (Opus 5.5) → parallel implementation seats (Codex `gpt-6.2-sol`, medium, personal account; GLM-5.3-Flash on OpenCode Go, free model when Go is out) → review (Opus 5.5); Codex model and effort updated 2026-11-18. Hard edge-case bugs start from Codex | Owner's rule (`AGENTS.md`) | 13 |

## 3. Layers and repository layout

```
ararat/
  core/            Rust workspace: ararat-core (model, rules, coordinator, import, sync client), ararat-ffi (UniFFI + C ABI)
  server/          Rust: the sync relay (phase 8)
  engine/
    build-inputs.toml  the pinned build identity (4.7)
    ararat/        our in-tree layer, copied to //ararat/core
    chrome/        our files under //chrome/browser/ararat
    patches/       series + patches against the base
    scripts/       apply (series, then our layer rsynced in), series-check, gen, build, smoke
  macos/           one SwiftPM package
    Sources/ararat_ffiFFI/  C module for the core's UniFFI header; links the Rust static library
    Sources/AraratKit/      Swift adapter over the core bindings (generated) and, later, the engine API
    Sources/AraratUI/       AppKit + SwiftUI components (library)
    Sources/AraratHarness/  UI harness: real components on real core data, a placeholder where the page goes
    scripts/build-core.sh   builds the core and regenerates the bindings
    Sources/Ararat/         the app's launcher executable: loads the framework, calls ChromeMain
    scripts/bundle-app.sh   stages the engine's Chromium.app as Ararat.app and signs it ad-hoc
  docs/
```

The harness is a permanent development tool, not a stand-in for the app, so UI work never waits for a Chromium build. Cra's command file and Ardia's dev harness play the same role.

### Dependency directions

```
macOS App ──► AraratUI ──► AraratKit ──► ararat-ffi ──► ararat-core
                               │
                               └──► engine ObjC API (//ararat/core) ──► Chromium //chrome
```

- `ararat-core` depends on nothing platform-specific and never calls the engine or the UI. It decides; adapters execute.
- `AraratUI` never calls the engine directly. Only `AraratKit` holds engine and core handles.
- `AraratKit` is a thin adapter: it forwards engine transactions to the core's coordinator and executes the engine commands the coordinator returns. Rules live in the core, so Windows and Linux reimplement only the adapter.
- On macOS the engine does not link the core; the adapter bridges them inside the same browser process. On Windows and Linux the Views UI links the core through its C ABI (section 10).
- Chrome's files know only our hook header (4.3), never our classes.

## 4. Engine

### 4.1 What is tightly coupled and what is isolated

| Part | Coupling | Where | Rule |
|---|---|---|---|
| Our `BrowserWindow`, `BrowserDelegate`, UI seam implementations, session persistence, ObjC API | Tight, inside the tree | `//ararat/core`, `//chrome/browser/ararat` | New files only. Built with Chrome's GN rules |
| Edits to Chrome's own files | Minimal, isolated as hooks | `engine/patches/` | Each edit is a function-pointer hook declared in one shared header; one concern per patch |
| Base patch set (ungoogled-chromium) | Imported, guarded | `engine/patches/series` | A skip list plus guards check that skipped patches stay out and that nothing touches what the skips protect |
| Rust core, sync, import | Isolated | `core/` | No Chromium types |
| AppKit UI | Isolated | `macos/` | Talks to the engine only through `AraratKit` |

### 4.2 Base and patch management

- The clean Chromium revision and the base patch set are pinned separately in `engine/build-inputs.toml`.
- The base is ungoogled-chromium (the owner's choice, 2026-11-04, over Helium; reasons in section 1). The inventory of every ungoogled-chromium patch, marked kept, skipped or counter-patched with its security consequence, is `docs/research/ungoogled-inventory.md` §8. Phase 2 builds selected upstream patches and our patches (the counter-patch that keeps the component updater is §8.6 there; the other, `ararat/remove-screenai-sandbox-parameter.patch`, deletes the ScreenAI branch — the sandbox parameter that would point at its component binary — from `chrome/browser/chrome_content_browser_client.cc`): Google Safe Browsing stays in the build until the owner picks the reputation source (14), so the extension kill switch of 9 holds; no domain substitution and no binary pruning (ours, provisional). The pinned version is 157.0.8103.39, after the one rebase phase 2 measured (below).
- Helium was the provisional base until then. If the inventory or the rebase shows ungoogled-chromium costing more than expected, Helium is the alternative to compare, skipping what fights our choices as Ardia does (Ardia ledger 1.2).
- `engine/patches/series` is the only source of patch order. Patch names state their concern; no ordering prefixes.
- The patch files themselves are vendored under `engine/patches/ungoogled/{generic,macos}/` from the pinned ungoogled commits, both projects' BSD-3 LICENSE files kept alongside: the generic ones byte-identical from the head of ungoogled-chromium's 157 pull request (#4032, merged 2026-11-04 as tag `157.0.8103.38-1`; its merge commit is the vendored head, so no re-vendoring is needed), the macOS ones from 156's macOS commit with `disable-crashpad-handler.patch` rebased by hand to 157. `engine/patches/README.md` lists the commits. `engine/patches/ararat/` is where our own patches live.
- The series is applied and verified by the bash scripts in `engine/scripts/`: `env.sh` holds the shared environment, `fetch` takes the pinned tag and syncs DEPS, `apply` resets and applies the series with no fuzz and copies the layer in (`engine/ararat/` → `src/ararat/core/`, `engine/chrome/` → `src/chrome/browser/ararat/`), `series-check` verifies the series' bytes and the copied layer, `gen` writes the args and runs gn, `build` takes the lock and runs autoninja, `smoke` runs the app headless.
- `series-check` compares, read-only, every file the series touches and the copied layer files against the manifest of SHA-256 hashes recorded at the last good apply (`engine/patch-state.sha256`, committed under `engine/`), and refuses a stray file in the copied layer directories; it resets nothing and applies nothing, and also refuses when the manifest was recorded for a different series. `build` runs it before its own work and, on any difference, stops and says to run `apply` — `build` never resets the tree or re-applies patches. It runs before every engine build.
- `apply` writes a patched file only when its bytes differ from what is on disk: when the tree already matches the manifest and the series has not changed, it writes nothing and every mtime is left alone; otherwise it resets the tree to pristine (src and every DEPS repository the series touches), applies the whole series in order with no fuzz, and rewrites the manifest. On the first failure it names the patch and the file and exits, leaving the tree reset, not half-patched.
- Ours, `ararat/restore-component-updater.patch`, reverses only block-requests' hunk in `components/update_client/update_checker.cc`, so that file comes back byte-identical to stock after `apply` (checked on 156).
- The source comes from git + gclient at the pinned tag with Chromium's own pinned toolchains, and ungoogled's `pruning.list` is not run — it would delete the prebuilt toolchains gclient installs.
- PGO: the mac-arm profile pinned for 156 in `chrome/build/mac-arm.pgo.txt` (about 88.9 MB) is on the public optimization-profiles bucket and the gclient hook can fetch it, but only when `checkout_pgo_profiles` is set in `.gclient` — `gn gen` with `chrome_pgo_phase=2` otherwise refuses. Phase 2 runs `chrome_pgo_phase=0` and the profile was not downloaded; whether to pay the download is design's call.
- Applying the series took 11 s on the 156 tree (2026-11-05, reset included). The no-op re-apply that keeps every mtime takes about 10 s, all of it verification.
- Rebase to 157.0.8103.39 (2026-11-05, measured once): fetch and DEPS sync 5 min 45 s; the 14 generic patches that no longer applied were taken from ungoogled-chromium's 157 pull request (#4032, which targets 157.0.8103.38) and `disable-crashpad-handler.patch` was rebased by hand, because crashpad's `InitialStart` gained an `embedder_port` parameter; then the patches applied without fuzz across 129 files, about 8 min from the start of the fetch. Our patches applied unchanged.
- Large edits to Chrome files are rewritten as a new class plus a small hook (Ardia rewrote a 1,012-line PiP patch this way).
- The metric is the number of hunks inside Chrome's files, not the number of patches.

### 4.3 Hooks

Hooks are `g_ararat_*` function pointers declared in `ararat_hooks.h`. Chrome's patched files include that header except for `g_ararat_is_window` and `g_ararat_history_deleting`, which are defined without it in the read-anything controller and HistoryService respectively; their signatures are not checked against the declaration at compile time. Unset, Chrome behaves as stock. The history deletion hook runs before HistoryService schedules explicit deletion. The list today: `g_ararat_is_window` identifies our windows for the read-anything viewless path; `g_ararat_add_browser_main_extra_parts` in `chrome/browser/chrome_content_browser_client.cc` hands the browser main parts the client created to our layer, which adds its own `ChromeBrowserMainExtraParts` through `AddParts`; `g_ararat_create_browser_window` in `chrome/browser/ui/browser.cc` is always installed and routes supported Browsers to our hosts. `g_ararat_reopen`, `g_ararat_dock_menu`, and `g_ararat_open_urls` handle Dock reopen, the Dock menu, and external URLs; `g_ararat_shown_browser` identifies the shown Browser for AppController. `g_ararat_create_permission_prompt` routes permission requests to our tab-modal prompt. The window factory hook takes `BrowserWindowInterface*`, not `Browser*`: upstream restricts `browser.h` (`browser_header`'s visibility) to move callers to the interface, and our layer needs only the interface. Every exported name is listed in both `ararat.exports` (the linker's `-exported_symbols_list`) and the symbols `link-ararat-layer.patch` adds to `chrome/app/framework.order`, because `verify_order.py` refuses any framework export the order file does not list; the scripts refuse a difference between the two lists, and a name with no definition in `engine/ararat/` (ours).

### 4.4 Engine ↔ app API

U17b adds `openURL:commandId:itemId:profile:external:untrusted:historyStamp:`, `AraratPurgeTabHistory`, `AraratFinishCrashRecovery`, `AraratCheckTabHistoryFile`, `AraratCheckDeleteHistory`, `AraratCheckCrashState`, `AraratCheckCommitProfilePrefs` and the tab's `checkFlushHistory:`. Flush success means the atomic file write completed. The profile preferences commit check waits for Chromium's write reply before the crash seed reports ready.

- U27w adds `AraratApplySiteDefaults`, `AraratSiteExceptions`, `AraratSetSiteException` and `AraratClearSiteData` to AraratHostAPI.h — a settings pane acts on every regular profile, so these are C entry points rather than `ARWindowHostAPI` methods. The seven defaults are the app's synced settings record pushed into each profile's `HostContentSettingsMap` default (and into a profile the engine creates later); the list is the pref provider's single-origin rules of the seven kinds; a write is `SetPermissionSettingDefaultScope` for that origin and kind (a nil setting resets it); a site clear is one `BrowsingDataRemover` task with a registrable-domain filter and the cookies, DOM storage and cache mask, whose reply is the failed data types bitmask, not a count. Checked by `settings-websites` (ours; runtime verification pending).
- U27p adds `AraratApplyPrivacySettings`, `AraratClearBrowsingData`, `AraratCheckSeedHistoryVisit` and `AraratCheckHistoryVisitTimes` to AraratHostAPI.h, again as C entry points because the pane acts on every profile. The record is the cookie-controls pref (Block or the off mode), the `universal_optout.enabled` GPC pref and the history retention in days (0 keeps everything: the pane's Forever and the state before the first apply, with the expiry loop at the five-minute cadence so a retention set later takes effect within about five minutes; a positive value is days); it is applied to every loaded regular profile now and to one added later. Clear is one `BrowsingDataRemover` task with the app's three type bits (history, cookies and other site data, cache) and a time range, whose reply is the failed data types bitmask; the history part reaches the existing deletion observer, so the U26d banner path stays the only failure surface. The two check entries add a visit at a chosen age and list a URL's visit times for the VM's retention and clear conditions. Checked by `settings-privacy` (ours; runtime verification pending).
- P5b adds `AraratApplyDownloadSettings(directory, prompt)` to AraratHostAPI.h, again as a C entry point because Settings › General's downloads rows act on every regular profile. `prefs::kDownloadDefaultDirectory` and `prefs::kPromptForDownload` are written into every loaded regular profile now and into one the engine creates later (the `ProfileManagerObserver` route the Privacy entry uses); an empty directory clears `kDownloadDefaultDirectory`, so Chromium's own Downloads folder applies instead of a folder set in Chromium's own settings, and a relative one is refused before the call (the core refuses it too). Private profiles keep their own rule: `AraratConfigurePrivateDownloads` copies the regular profile's folder and never prompts. Checked by `settings-general`, which reads the prefs back through the existing check-only `downloadsCheckSettings` (ours; runtime verification pending).
- U27x adds `AraratExtensions`, `AraratSetExtensionEnabled`, `AraratSetExtensionSiteAccess`, `AraratSetExtensionPinned`, `AraratReviewExtension`, `AraratRemoveExtension` and `AraratSetExtensionsChangedHandler` to AraratHostAPI.h, again as C entry points because the pane acts on a profile. The list is the profile's `ExtensionRegistry` filtered by `ui_util::ShouldDisplayInExtensionSettings` — what Chromium's own extensions page shows, so component extensions are out and Web Store, unpacked and external-pref installs are in — plus terminated entries: id, name, icon (the manifest's icon, read once on the UI thread), enabled, disable reasons, `needsReview` (`DISABLE_PERMISSIONS_INCREASE`), site access from `PermissionsManager` and `ExtensionPrefs` ("none" when the extension requests no site access, "all" without withheld permissions, "click" with withheld permissions and no granted hosts, otherwise "specific"), the toolbar action's pin state and `canPin`, `canDisable` (Chromium's own rule for offering the switch: `UserMayModifySettings`, not blocklisted, no dependent extensions, and none of Chrome's pinning disable reasons including a suspicious install) and `removable`. A profile that exists but whose space has not been shown since launch is loaded on demand with `ProfileManager::LoadProfileByPath`, which never creates one; a path with no profile-attributes entry answers an empty list without a load (its callback would be the synchronous null one and would re-list forever); while a load runs the list is the one-entry `loading` reply and the pane keeps its rows, and only a load that produced a profile notifies through the watcher. Enable and disable go through `ExtensionRegistrar`; a policy-held extension answers "policy", and an extension disabled for a permissions increase answers "review" instead of enabling. Site access writes `ScriptingPermissionsModifier` (withhold off for all sites; withhold on and all grants dropped for on click); a site-by-site choice stays Chromium's page. Pinning writes the profile's `ToolbarActionsModel`. Review… shows `ExtensionInstallPrompt` with `GetReEnablePromptTypeForExtension` and grants and enables on accept. Remove… is the pane's own AppKit sheet on the settings window; accepting calls `AraratRemoveExtension(profile, identifier)`, which looks the extension up immediately before the call and then uses `ExtensionRegistrar::UninstallExtension` with `UNINSTALL_REASON_USER_INITIATED` (the registrar re-applies the policy). The change handler is one registry observer over every regular profile plus one `ToolbarActionsModel` observer per profile, so the pane follows installs, removals and switches made elsewhere and a pin made from the URL field; the model's initialized, action-added, action-removed and pinned-changed events re-list the pane. `AraratCheckLoadUnpackedExtension`, `AraratCheckDisableExtensionForReview` and `AraratCheckExtensionDialog` are the check-only seams the VM uses: unpacked updates are trusted locations, so Chromium never disables one for a permission increase, the install turns the scratch profile's extensions developer mode on (Chrome disables an unpacked extension while developer mode is off; a `--load-extension` fixture is `kCommandLine` and needs no switch), and the dialog seam accepts the Views dialog only when it is the re-enable prompt (`ExtensionInstallDialogView`, its class name is what the check asserts), because the VM's in-process accessibility tree is empty; the pane's Remove sheet is AppKit and needs no seam. Checked by `settings-extensions` (ours; runtime verification pending).
- Each tab exposes the navigation controller's entry count and `canGoBack`, separately from the process-local navigation counter. The strip reports renderer-crash state; selecting a crashed tab requests a reload, including when it is already active (ours; runtime verification pending).
- The host delegate reports page fullscreen and the native window's target fullscreen state separately. The native widget reports transition completion to the Browser that started the transition and to the shown Browser if it changed; the exclusive-access context reports tab fullscreen, including a pending request, to the app. Hidden checks simulate the window state and synchronize the shown Browser's tab renderers without showing the host (U15, ours).
- The framework implements Objective-C classes in `//ararat/core` (for example `ARWindowHost`, `ARTab`, `ARPasswords`, and the planned `ARProfile`, `ARExtensions`, `ARDownloads` and `ARAutocomplete`). Swift imports the app-facing protocols through SwiftPM and resolves `AraratWindowHostCreate(contentView, windowId)` from the loaded framework with `dlsym`; it calls the resulting host and tabs through those protocols (ours).
- The layer supplies a modal dialog host positioned over the page card. In the default c1 compositor, the card holds the visible page views, divider and placeholder views, and the modal host's position view. In c2 the page uses the shared compositor instead. `g_ararat_create_permission_prompt` installs our tab-modal `PermissionPrompt` sheet; Swift UI replaces that sheet in phase 4. Each Browser registers our Autofill bubble handler on unowned user data for save-address and save-card prompts (ours).
- Our `DevtoolsUIController` has an empty container list; `devtools-hook.patch` calls `g_ararat_devtools_changed` from `DevtoolsUIController::UpdateDevtools`. The engine layer owns docked layout: the DevTools view stays full-size, with the page at the y-flipped strategy rect. In c2 a clip excludes the page rect from the DevTools view because the page is in the shared compositor below the app's views. Layout updates on resize and every hook call. The check-gated `AraratHostAPI.h` entries open and close DevTools, inspect its state and tab state, undock and redock it, count its hosts, and invoke Inspect Element (ours).
- The tab API takes the coordinator's IDs: the app supplies the workspace window ID to `AraratWindowHostCreate`, and `openURL:commandId:itemId:` returns whether the open was accepted (done or queued); the app finds the opened tab through `-tabs` by its live ID, which is the command ID, and `activateWithCommandId:`, `closeWithCommandId:` and `setItemId:` act on it. An open during Browser destruction is queued in FIFO order. An open whose completion transaction lacks its live ID failed: a failed accepted open is reported as a transaction — the next revision, cause `Command(<the open's id>)`, carrying the window's strip as it is now, or an empty strip when the window has no Browser — and a rejected open (closed host, no epoch, invalid URL and so on) returns `NO` and emits nothing. A tab created by Chrome receives a `chrome-` UUID and no item ID. `ARWindowHost` obtains the page card from its delegate and reports `{epoch, rev, cause, strips}` through it (ours).
- `pageCardForWindowHost:` must be a plain getter, and KVO observers must dispatch tab commands asynchronously (ours).
- The Browser factory synchronously requests a host through `create_host`; open URLs and Handoff use `open_urls`. External opens carry Chrome's untrusted-launch flag so the engine preserves its opaque initiator. Strips carry the opener's live ID, the committed URL and page title, and whether a navigation was newly committed. Title and navigation changes send another transaction (ours).
- Opens carry the item's profile even if the user switches spaces before the command reaches the engine. The host delegate's `showProfile` request switches the window to its most recently shown space for that profile (ours).
- The feed has one epoch per engine process, based on its start time, and one revision counter. Setting the first host's delegate synchronously reports an empty rev-0 snapshot with cause `Engine`; until that first delegate is set, tab commands do nothing and `openURL:` returns `NO`. Subsequent changes increment the revision. A closed window is reported with an empty strip and cause `Engine`, clearing live mappings without closing workspace rows; omitting the window leaves it unchanged (ours).
- Each command produces exactly one transaction carrying its cause; a second one is dropped (ours).
- Contract for every class: main-thread affinity (calls from other threads are a programming error and abort in debug builds); objects that wrap Chrome objects are invalidated when the Chrome object dies; Swift owns wrappers, the engine owns Chrome objects. Invalidated `ARTab` command calls are silent no-ops. Transaction delivery holds the host weakly and is posted to the main queue after the initial snapshot; fullscreen state delivery is synchronous (ours).
- Services the UI needs (passwords, autofill, extensions, zoom, search engines, history, bookmarks, downloads) are called directly on Chrome's services from our layer. We never script `chrome://` WebUI pages (Ardia ledger 1.4).

- Settings › Passwords is a native pane for the current regular Chromium profile. `ARPasswords` wraps the profile store and `SavedPasswordsPresenter` on the UI sequence. The saved list starts locked. After device authentication it distinguishes loading, failure and an empty or populated list. Each row carries an opaque ID, website and username. Search is local to the pane. The engine resolves IDs within the profile to add, edit, delete and reveal passwords. The user name and revealed password are edited on the detail page. Hide asks before discarding an edited password. Discard clears the password field and leaves any user-name edit for Save Changes. Closing or retargeting Settings resets the pane's authorization and invalidates the handle, IDs and pending callbacks.
- The per-profile `ararat.password_manager_enabled` preference defaults on. Off stops Chromium's built-in password saving, filling, and generation and invalidates cached fill data in open tabs. Private tabs read the original profile's preference. Entering a URL with the `chrome://password-manager` host or opening it from Ararat's UI opens Settings › Passwords. Chromium blocks links and scripts from web pages through `CanDisplay` and the renderer URL filter. The Password Manager WebUI is disabled. The Offer to save switch sets Chromium's `kCredentialsEnableService`. The Fill passwords switch appears once Chromium has recorded biometric availability in `kHadBiometricsAvailable`. Every change to `kBiometricAuthenticationBeforeFilling` requires fresh device authentication, with a validity period of zero. When enabled at the Chromium pin, it suppresses automatic prefill and gates filling from password suggestions, HTTP authentication and Credential Management API `get()` on device authentication. Auto sign-in has its own preference.
- The browser shows password offers in a Chromium Views tab-modal dialog at the top centre of the page card. The dialog blocks page input, takes focus and returns it on close. Return activates Save or Update, Esc activates Not Now, and clicks outside leave the dialog open. The dialog shows the site, an editable user name and a masked editable password. Chromium controls reauthentication before revealing and whether the edited credential is a new login or an update. An empty password disables Save and Update. Never for This Site is available on a new-login offer while it still targets a new login. Chromium routes the write to the store. Ararat’s shipped profile uses its local store. Chromium’s automatic save and update confirmation states display a read-only dialog. A background tab’s offer waits for activation, and a displayed offer reappears when its tab is selected again. Chromium counts implicit and explicit dismissals of automatic save offers towards the smart-bubble threshold for the same site origin and user name. The current tab’s key button reopens a suppressed or dismissed offer in the sidebar URL field or Little Window bar. The focused-tab action is also available in the command bar when the sidebar is hidden or fullscreen. Cross-site commits, replacement submissions, Never for This Site and revoking either password preference invalidate recovery. The engine checks both preferences, off-the-record state and the current offer before presenting or acting on it. The `password-prompt` screen check uses real fixture forms with a scratch profile, workspace database and mock Keychain.
- Unlock and reveal use Chromium's `ChromeDeviceAuthenticatorFactory` and `DeviceAuthenticatorMac`. This uses Chromium's five-minute per-profile reuse window and its macOS authentication policy, which can use Touch ID or a companion Watch and can fall back to the macOS login password. Opening a new pane session still requires an unlock action. The `passwords` scratch-profile check fakes the device-auth result, sets `kHadBiometricsAvailable`, and exercises the fill preference and Chromium store with the mock Keychain. Real Touch ID is unverified.
- The `passwords-real-auth` screen check exercises the macOS password fallback on the VM with a fresh scratch profile and workspace, the mock Keychain, and a fixture sign-in. It checks that Fill passwords is hidden and that cancelling the system prompt leaves the pane locked. It captures the system prompt before any password entry. The guest runner can supply `ARARAT_CHECK_VM_PASSWORD` in the app's environment to try unlocking and revealing the fixture within the reuse window. The result lists `password_unlocks` under `unverified` only when the variable is missing or empty, or when writing AXValue to the password field returns an AXError. If AXPress succeeds and the authorization dialog stays open, the check records a refusal and fails `password_unlocks`.
- Each normal app-hosted Browser registers an `ExtensionsContainer` for its profile. The overflow row uses 32 pt filled tiles on the favourites’ columns with 16 pt icons. The app lists action IDs, names and icons, and before running an action it sets the anchor rect to the clicked action's tile in the URL field or the overflow row; an action reached without a tile (its list is the site-controls grid, not built yet) is anchored at the whole URL field (ours). ### 4.5 Process and run loop

The AppController hook resolves the shown Browser for the main window, so its last profile and menu target follow profile switches. Native openURLs and Handoff validate the profile through Chrome's safe-profile path before dispatch (ours).

- On `started`, the app opens the workspace, builds the sidebar and page card inside `SidebarContainerView`, creates the host and attaches the engine adapter. On `will_shut_down`, it detaches the adapter and releases the host on the main thread (ours).
- The bundle's launcher executable (`Sources/Ararat`) loads the framework; the browser process calls our `AraratMain` (which stores the launcher's callbacks, sets the extra-parts hook and calls `ChromeMain`), the helpers call `ChromeMain` stock. The hook adds our `ChromeBrowserMainExtraParts` to the stock client's parts, and they call the launcher's `started` callback at `PostBrowserStart` and `will_shut_down` at `PostMainMessageLoopRun`: `started` fires inside `PreMainMessageLoopRun`, after the startup browsers open and before the main loop runs, so a handler must not assume the loop is running. `AraratQuit` is callable from anywhere; before the loop is near, the request waits for the started stage. `--ararat-check=<name>` runs only with a `--user-data-dir` under `$TMPDIR` and `--use-mock-keychain`, else it exits 2; `started` prints one JSON line `{"check":"started","ok":true,"browsers":N}` and quits; `window` checks a hidden host, its native window and hit test, then waits for Browser destruction. `NSApp` is Chrome's `BrowserCrApplication`. Nothing touches `NSApp` before Chromium starts, and the AppKit UI is created from a Chromium startup callback (ours).
- Chrome's `AppController` remains the application delegate and owns quit, logout, download confirmation and the keep-alive with no window. The layer intercepts Dock reopen, Dock menu and the downloads-wait case with no Browser. `AraratMain` adds `--no-startup-window` before calling Chrome, and the app handles reopen through its callback. External opens from `application:openURLs:`, Handoff, launch arguments and a second launch's ProcessSingleton notification share one app entry, which queues URLs until the workspace is ready and calls the core's `route(url)` for each, in order. Native openURLs and Handoff use the original regular profile even when a private window was last active; forced-incognito policy and explicit incognito command-line opens keep the engine's off-the-record path. A space destination uses a regular window already showing that space, else the key regular window of its profile switched to the space, else a reopened or new window. It creates a foreground tab at the top of Today, selects it and brings the window front. A rule's Most Recent resolves within that rule's profile in the core. The default Most Recent uses the key regular window's space, else the most recently kept regular window's space; with no regular window open, it uses the most recently used space across profiles. A Little Window destination opens in its specified profile at the remembered frame. Profiles load through the engine when needed; the core supplies the deleted-space fallback. Several URLs each route independently and the last takes focus; both destinations preserve `untrusted`. Routing never edits rules or the default. The bundle's display name and name are Ararat. The `atc-routing` VM check uses the real AppKit open-URLs delegate, cold-launch arguments and a second process; `--ararat-atc-launchservices` also checks `open -a`. Launch it with `--ararat-check=atc-routing --use-mock-keychain --user-data-dir=<scratch> --ararat-db=<scratch-db> https://atc-space.test/cold` (the scratch paths must meet the existing guards). Engine build and VM execution remain required to verify these paths. At launch, Restore windows and tabs restores every kept regular `Window` record in stored order, oldest first and newest last so the newest window becomes key; no kept record means one fresh UUID. Open a new window instead captures the newest kept record's shown space across profiles, discards all kept window records, and opens one fresh UUID on that space. It restores no old selection or presentation and acknowledges crash recovery directly; workspace spaces and tab rows remain. Dock reopen adopts the newest kept record no open window uses and restores its selection and presentation, else a fresh one. Each record keeps the shown space, validated selection, last non-empty normal frame, sidebar width and hidden state (including transient floating reveals) on this device, outside the sync journal. Move, resize, sidebar changes and close save the presentation; fullscreen keeps the normal presentation. Restoration applies it before showing the window and clamps its frame onto the screen with the largest intersection (the main screen when the old display is gone). Every window write stamps its time, which orders newest. Private windows do not persist. A window the user closes deletes its `Window` record, and quit keeps every `Window` record (unit 46's rule for rows, so record ids are never reused). Quitting and closing a window leave workspace tab rows unchanged; a cancelled close keeps its host and Browser (ours).

### 4.6 Windows, tabs and the duties we take over from Chrome's UI

Each host keeps one Browser and profile keep-alive per profile it has shown. A strip contains every hosted profile's tabs, each tagged with its profile; its active id belongs to the shown Browser. The `showProfile` delegate switches to the window's most recently shown space for that profile, and the host switches the page and reports activation to Chrome (ours).

A hidden workspace page normally reports no active tab. A foreground Open's completion strip reports the tab it opened even while the page is hidden, only when the command id, live id and item id match the active tab. Remote pages remain masked. Background Opens and later hidden-page snapshots retain the mask (ours).

**Windows and profiles.**

- One app window is one Views-backed `NSWindow` (`NativeWidgetMacNSWindow`), so Chrome's bubbles, dialogs, menus and autofill dropdowns attach to it as child windows.
- The window is titled, closable, miniaturizable and resizable, with full-size content, a transparent titlebar and no visible title. The sidebar owns the traffic lights; AppKit's own buttons are hidden except in full screen (ours).
- A regular or private workspace window uses the displayed page's title or, when it shows no page, the selected space's name (ours).
- Each profile shown in the window has its own Chrome `Browser` whose `BrowserWindow` is our object with no `BrowserView`, frame, tab strip or toolbar.
- Extension window semantics: each profile `Browser` has a separate extension window id. The shown Browser in the key window is active; the shown Browser in each other app window is unfocused but not minimised. Hidden Browsers report inactive, invisible and not minimised, with the host window's bounds. Deactivating the app unfocuses all Browsers. `currentWindow` for an extension's own context is the Browser containing it; for a background context it is the focused Browser, or the last focused one while the app is inactive. `windows.update({focused: true})` for a hidden profile switches to its most recently shown space in the window. Whether Arc exposes all of a profile's tabs or only the current space's tabs is unverified (ours).
- On app deactivation, `windows.onFocusChanged` delivers `WINDOW_ID_NONE`; when a window becomes key again it delivers that Browser's window id. Switching between Ararat windows does not itself signal app deactivation. A switch to another profile's window delivers `WINDOW_ID_NONE` to the previous profile's extensions, as in Chrome. Chromium's profile and incognito visibility rules apply (ours; engine verification pending).
- Extension popup windows (`windows.create({type: "popup"})`) stay real popup windows (Cra ledger 10). Our internal helper windows are hidden from extensions (Ardia ledger 1.7). Profile `Browser`s are not internal: extensions see them.

The current `AraratBrowserWindow` delegates window visibility, activation, bounds, title and native window operations to the host Widget and routes closing through Chromium's unload controller. Toolbar, location bar and other UI duties without an implementation return empty results or do nothing. Tab-modal dialogs use the page-card host (ours). `ARWindowHost` embeds the supplied `NSView` in a `NativeViewHost`; the app retains the host until the Browser is destroyed (ours).

**Tabs.**

- With C1, the page card hosts the selected tab or all shown split members. Other views leave the view tree and their `WebContents` are marked hidden. Closing the final tab destroys its Browser while the host stays open; the next open creates a Browser in the same epoch (ours).
- Which compositor owns a tab's `WebContentsViewCocoa` (per tab view, per profile, or shared per window) is a spike decision, because Ardia found that per-view compositors cost 1–2 refreshes on every tab switch and that changing later means a rendering rewrite (Ardia ledger 1.3, 1.6). - New contents: renderer-created windows reach us through `AddNewContents` with an existing `WebContents` and its pending navigation state preserved; modified clicks and form targets may take other paths (`OpenURLFromTab`). - One page, one place. A live page is shown in one place. A window selecting a page owned by another transfers its `TabModel` within the same profile; the source pane shows a short-lived captured snapshot or a neutral placeholder. A window becoming key takes back its selected pages. If a live transaction changes the owner of the selected tab or a pane in the selected split to another window, the key window rechecks whether to take it back after applying the transaction. It rechecks while it is still key and the selection generation is unchanged, provided there is no pending selection for another tab. The recheck is deferred: it runs on each window whose selected tab or a pane of its selected split changed owner, once the transaction has been applied, and only while that window is still key, its selection generation is unchanged, no selection is deferred and no Little Window handoff is in flight, matched to the selection it was decided for, so a selection that moved in between is not taken back. After close confirmation, pages still shown elsewhere are handed off before the window closes. Source and destination strips are reported together so a temporary detach is not treated as a close (ours; native verification pending).

**Sessions.** At app launch, Restore windows and tabs restores all kept regular windows, oldest first; Open a new window discards their records after taking the newest record's shown space and creates one fresh window there, acknowledging crash recovery without waiting for old windows. Chrome's automatic window restore is disabled for our `Browser`s. The factory patch disables it for every Browser when the hook is set. While a profile is hosted, the layer pins its startup preference to Chrome's default and resets changes, so a restore request without a Browser cannot reopen Chrome's session. Chrome's mandatory managed policy takes precedence over this setting. Per-row navigation history persists through relaunch and crash (U17b). Its history files are keyed by profile and core item id; closing, archiving or deleting queues file deletion. An unload keeps the file. Restoration requires the file's URL to match the row's URL, so a moved pinned row reloads its saved URL fresh. sessionStorage is not restored. PageState recovery is best effort: renderer updates may arrive late, and Chromium sanitizes and excludes some state (ours).

For crashed regular profiles the engine holds Chromium's `CrashedLock` until every restored window has finished its workspace restoration and the shared session calls `AraratFinishCrashRecovery`; if a profile is destroyed before recovery, it abandons the lock without acknowledging the crash. An explicit deletion invalidates once at request and again at notification, so a writer bound between them is fenced. If a dispatched restore is cancelled and no later transaction is applied, acknowledgement remains pending and the next launch may report another crash. These paths are unverified (ours).

The `relaunch-windows` two-run check creates three windows with distinct spaces, frames and sidebar widths, one hidden sidebar and one two-pane split, quits, then compares the restored ids, spaces, selections, presentations and pane counts. `history-clear` and `history-purge` use their existing self-contained data-URL fixtures and history-file probes. The `relaunch-windows-new` two-run check uses the same seed with startup set to Open a new window; run 2 checks one fresh id, the newest seeded record's space, only the fresh kept record, empty restore queues and a fired crash acknowledgement with none pending. Both window checks use self-contained data URLs and need no server or extension fixture. The VM exit suite must run all four; runner integration and execution of these checks for P5c remain pending.

The stamp changes on every layer edit, so a layer edit changes the release args and the next `out/Ararat` build regenerates and relinks; `build` refuses with a run-`gen` message when an args.gn carries a stamp older than the tree.
- `build` runs the read-only series check first and, when the tree no longer reproduces the recorded bytes, stops and says to run `apply` without touching the tree (it never resets or re-applies); otherwise it takes the lock and runs `autoninja -C out/Ararat chrome` under the job cap above, prints the elapsed time and step count, and appends a one-line JSON record to `~/chromium-build/build-times.jsonl`.
- `smoke` runs the built app twice with a disposable profile under `$TMPDIR` and `--use-mock-keychain` (with the real login keychain an out/Dev build exits 2 on "Teardown watchdog expired" after printing the DOM, and the keychain gains a "Chromium Safe Storage" item): `--headless=new --dump-dom` on a data: URL and `--version`. Either failure exits non-zero.

Phase 2's `engine/args.gn` is ungoogled's `flags.gn` + `flags.macos.gn` plus our `target_cpu="arm64"`, with `chrome_pgo_phase` provisionally 0 and no API keys; branding is settled in phase 3.
- `engine/build-inputs.toml` records the Chromium tag and commit, the vendored ungoogled commits and `ungoogled_tag`, the GN args path and SHA-256, the Xcode and SDK versions and build numbers, and the architecture. The commit is the authoritative pin for the generic ungoogled patch set. `ungoogled_tag` is its human-readable tag, which release-watch compares with the upstream tag. `engine/patch-state.sha256` records the series SHA-256 and the hashes of patched and copied files. Chromium's pinned tree supplies DEPS.
- Before releasing, run `apply` and commit the updated `engine/patch-state.sha256`. Build the engine locally from that commit.
- The `release.sh` script (§12) calls `bundle-app.sh --release`, which requires a clean checkout and runs `engine/scripts/series-check --release` to check the repository layer and engine tree against the recorded manifest. It calls `engine/scripts/corresponding-source <out-dir>/Ararat-source` before bundling the app.

The README also gives the fetch URL for the source archive of the pinned Sparkle 2.10.1 revision, and the export carries its SHA-256. The full command fetches the pinned Chromium and DEPS, applies the series and copies the layer, then compares the generated manifest byte for byte with the recorded manifest.

### 4.8 Security and data integrity from day one

- The Safe Storage keychain item name is fixed in the first build and never changed. The key is never silently recreated: create only for a provably new profile, otherwise retry and fail closed (Ardia ledger 1.8).
- Chromium's `PasswordString` clears the UTF-16 string passed to its constructor. At the pin, its process-bound feature defaults off and its backing `std::u16string` has no zeroing guarantee. Process-bound backing also provides no process-bound encryption on macOS at this pin. `secure_value()` returns a `SecureU16String` whose allocator clears heap storage on deallocation. Ararat also wipes the used buffer explicitly, including inline short strings, after the reveal callback. The store and presenter keep their own Chromium copies. The bridge's ID map uses Chromium credential entries and drops them when the store changes or the handle is invalidated. These copies have Chromium's backing and deallocation behavior.
- Child processes run in the macOS sandbox.
- Nothing writes into the app bundle; release checks re-verify the signature after a launch.
- The automation channel for tests is unreachable from web pages, and test-only switches work only in non-distribution builds with a scratch data directory (Cra ledger 33, Ardia ledger 1.8).
- WebRTC exposes no local IP: mDNS off, `default_public_interface_only` (Cra ledger 27).

### 4.9 Security maintenance

- A daily job detects new Chromium stable releases and new base-patch-set tags (Cra ledger 6). The check is `engine/scripts/release-watch`, which reads the pin from `engine/build-inputs.toml`, prints one JSON line and exits 10 when upstream is ahead; `.github/workflows/release-watch.yml` runs it daily and on dispatch and opens or updates a single issue titled after the new stable version.
- Patch-lag limits, counted from the upstream stable release: fixes for vulnerabilities exploited in the wild ship within 48 hours; other High and Critical fixes within 7 days.
- Security-only rebuilds on the same Chromium milestone are incremental and pre-authorised. Milestone bumps need a full build; whether they are pre-authorised is an owner decision (14).
- If the base patch set lags Chromium beyond the limit, we rebase onto the newer Chromium ourselves and carry the base patches.
- Rebase on a second build root: clone `src` without `out`, copy the gclient state, share depot_tools and the engine lock with the existing root, and use a separate Ararat branch so its patch manifest stays separate. Build and check on the second root; the owner decides the pin. Discarding the rehearsal means deleting the second root and branch with the owner's approval (ours). For the next rebase, check the hand-ported `disable-google-host-detection` deviation: the new suggestion URL getter remains active when its command-line switch is passed. At M162, the `sad_tab_controller` and `bubble_anchor_util_views` checks become fatal; retain the sad-tab guard and verify the bubble anchor invariant.
- Daily use by anyone, including the owner, requires: a working update path (Sparkle) and a URL and download reputation check (Safe Browsing or a chosen equivalent, 14).

## 5. State ownership

The workspace store is `--ararat-db=<path>` when supplied; otherwise it is `Ararat/workspace.sqlite` under Chrome's user data directory, obtained from the engine. Store calls run on one serial queue; engine calls run on the main thread (ours).

### 5.1 Who writes what

| Fact | Owner | Notes |
|---|---|---|
| Spaces, pinned/Today membership, favorites, folders, split items, archive, per-window view state, Air Traffic Control rules, key bindings | Rust core | Arc's model shape (components note 3) |
| Which `WebContents` exists, in which `Browser`, order, active tab | Chrome `TabStripModel` | Chrome commits; the app is never asked first, because extension APIs read their result back in the same call (Ardia ledger 1.4) |
| Navigation stacks | Engine session persistence (4.6) | Keyed by profile and core item id; sessionStorage is not restored |
| History, bookmarks, favicons, closed tabs, zoom, downloads, passwords, autofill | Chrome services | Never duplicated in the core |

- Workspace tabs that are not loaded have no `WebContents`.
- The coordinator in the core issues live-tab commands with ids. The engine replies with transactions `{epoch, rev, cause, strips}`: `epoch` changes on engine start; `rev` increases monotonically within an epoch; `cause` is our command id, our own engine call, or Chrome itself. One transaction never mixes causes. No echo windows, no "did we cause this" flags. A command stays in flight from its issue until the transaction naming its id arrives or the command is canceled; commands in flight are cleared when a new epoch starts, and a completion that names no command in flight is dropped.
- Changes Chrome makes on its own (an extension moves a tab, the successor after a close) are diffed and applied to the workspace by the core's rules; the successor follows the core's rule (split continuity, skipping tabs inside closed folders; a collapsed pinned section does not count, so its pins can be the successor and the holder rule then keeps that pin visible), not Chrome's choice. The successor is the most recently selected tab in that window, among the tabs of the space it shows, that is still open or unloaded and visible (closing never pages the sidebar to another space; measured in Arc), as in Arc (measured 2026-11-01 with ⌘W and with AppleScript: closing went back through the selection history, not to a neighbour; `docs/research/arc-ardia-observed.md` section 7). With no such tab, the nearest visible open or unloaded tab below the closed one in the same list, else above, else none (our fallback). An unloaded row is a successor the way a loaded one is: the close selects it, and the window loads it with the selection request a click makes, so exactly the successor loads (Arc keeps rows unloaded — the Arc import writes every row that way — and closing the only loaded tab of such a space selects the neighbouring row and loads it, as the owner measured, 2026-11-25). A row a close unloads, and every member of a split that close unloads, leaves that window's selection history: closing two pinned rows in a row moves on instead of reloading the one just unloaded. The core stores one selection per window. That selection names the selected member of a split, and the UI renders the outermost split (§4.6). Closing a split row closes its members together. ⌘W on a pinned tab or a favorite unloads it, keeps its row, and moves to the successor the same way. The selection history is per window, local, and not synced. The `close-successor` check imports an Arc sidebar, loads one Today tab, closes it and asserts that the neighbouring row is selected and loaded and that no other row of the import is.
- A transaction's strips name the windows they carry, and the coordinator's gone pass looks only at those windows: a tab that vanished from a window the transaction does not name is left alone (ours). A closed window is reported as an empty strip, so its tabs are seen as gone.
- Adoption places a tab at the end of Today in that profile's most recently shown space in the window; Arc's placement for link-opened tabs has not been verified. An active adopted tab becomes selected, except in an Engine-caused strip after the initial epoch snapshot; a background tab receives no selection stamp or successor-history entry. The core stores the reported URL and page title while retaining any custom title, on Today rows only: a live navigation never moves a Pinned or Favorite row's saved URL and title, as Arc keeps a pinned tab's URL — returning to the pinned URL is a later unit's work (ours). The opener ID travels in the strip but is not yet used for placement (ours).
- After the initial epoch snapshot, command confirmations and Chrome-caused strips update the per-window selection. Engine-caused strips update tab state and metadata without changing the selection: a profile switch can report that Browser's previous active tab before the requested activation. When a Chrome-caused close changes the window's selection, the strips' active tab is not recorded for that window — the successor the rule chose stands (ours). A command or Chrome strip whose active tab is not in the space the window currently shows is not recorded either, though its map and metadata effects stand: a selection made before the user switched space can land after the switch, and recording it would select a tab outside the shown space and leave the page empty. The coordinator then activates the row the window keeps selected once more, the close successor's shape, because the page follows Chrome's active tab and would otherwise show the space the window left under the shown space's sidebar; the strip that answers that activation names a tab of the shown space, so it records nothing and asks for no further command (ours). Each reactivation carries the ID of the window whose selection it restores. The adapter dispatches it only if the window is still attached, its selection generation is unchanged, and the target tab is still selected. A pending selection for a different tab cancels the reactivation. When a close and a click overlap, the click can complete without the close successor activating.
- Tab switching shows the page natively first; no round trip through UI state is on the display path.
- Air Traffic Control stays inside the rule's own profile: a rule rides in the profile that owned the routing file it was imported from (the caller passes the owner; without a known owner each rule takes the profile its space destination names, so the destination still belongs to the profile the rule rides in), its space destination must belong to that profile, a Little window destination names a profile the workspace has (the built-in one or a named one its records carry), an edit that breaks these is refused and an import skips that rule. A rule whose space was deleted still answers, first to the most recently used space of its own profile — the selection record's newest tab ranks the spaces — then to the default destination, then to the default profile's most recent space, and last to the most recent space (ours).

### 5.2 Crash consistency

- Live tab identities and the live-id map do not survive restart. Chrome session restore is disabled; the initial empty engine snapshot unloads absent rows. With Restore windows and tabs, every kept regular Window record opens its own window and its validated selected tab by item id and saved URL; its shown split members also open and recover their stored layout when the selection belongs to a split; other rows remain unloaded. A missing, closed or archived selection, a selection outside the shown space, an invalid ancestor or URL, or a failed or withdrawn Open leaves the card empty. Arc's relaunch behavior has not been measured (ours).
- Arc import writes new tab records as Unloaded. Reimport keeps the Open lifecycle of tabs already mapped to live engine tabs. Opening a committed space selection loads its selected tab and any shown split members. Preparation for scrolling between spaces builds sidebar views only.
- On start the engine reports a full snapshot for the new epoch; the coordinator reconciles it with the workspace. The workspace is the authority: each item records its lifecycle state (open, unloaded, closed, archived) in the same transaction as the change, and closes and archives are committed before the coordinator tells the engine. Each close or archive, including those of Close Split, Clear Today, auto-archive and Delete Space, saves the row's inverse; when a page refuses the close (beforeunload, Stay), the engine reports the cancelled command and the core restores that row's place, selection and live mapping, while the other rows of the batch stay closed; a refused row whose space was deleted returns to the Today of the space the window shows (p4stay). Engine tabs whose item is closed, archived or deleted are closed again, never adopted. Tabs that arrive without an item inside the epoch (⌘-click, `window.open`) are adopted into Today in that profile's most recently shown space in the window. Their URL remains empty until a committed navigation is reported. Adoption associates the live tab and item as WebContents user data. An unloaded row reported live is set open (ours).
- A transaction that is dropped — stale, repeated, from an old epoch, or one that would break the map's one-to-one shape — consumes its rev: a later transaction with the same rev is the engine's bug, not a retry (ours).
- Command completions carry the epoch they were issued in and are dropped if it is not the current one.
- Crash acknowledgement uses `CrashedLock` and `AraratFinishCrashRecovery`; destruction before recovery abandons the lock without acknowledging (§4.6). The crash check covers the acknowledgement; the abandon path is not exercised natively.
- Crash-loss window: a workspace change is durable when its SQLite transaction commits. Most edits flush before success; selection and space changes can wait for the one-second batch. Live reconciliation returns its in-memory outcome even if its flush fails, reports the persistence error, and retries the write. Failed writes extend the loss window until retry succeeds. Workspace changes and the outgoing sync log share a transaction.
- Disk full or a failed write keeps the in-memory state, retries with backoff and tells the user; it never truncates the database.
- Closing, archiving and deleting (archive entry, folder, space) record a durable local history-purge outbox with the workspace change; unloading does not. U17b adds a consumer and admission stamps so an older purge cannot delete a newer writer's file; the history-purge check exercises it natively. Restoration requires the file's URL to match the row's URL.
- Explicit history deletion invalidates the profile generation and fences existing writers; automatic expiration does not. Marker and file cleanup run on the history sequence. A crash before marker persistence or a deletion failure may leave old files. Deletion is ordinary filesystem deletion, not forensic erasure. Failures are logged and retried; a user-facing indicator is deferred to phase 4 (unverified).
- Backups use the SQLite backup API, so the WAL is included.

### 5.3 Private browsing

Phase 4 target: Off-the-record profiles are a property in the engine contract: every transaction and tab carries it. The core keeps off-the-record workspace state in memory only and rejects, in one place, any durable write, archive entry, sync record or command-bar learning for it. Tests cover close, crash, archive and sync with private tabs open.

Built in U26f passes 1-2: the engine sets `off_the_record` on every transaction and tab from `Browser::GetProfile()->IsOffTheRecord()`, and the core rejects a transaction whose flag is missing or does not match its tabs before any workspace change. A private workspace is a separate in-memory workspace with no store; one admission policy before every mutation allows tabs, selection, live state and reordering inside Today, turns close, archive and Clear into removal (no archive entry, no Undo, no recency, no history purge), and rejects import, settings, routing, extra spaces, folders, pins, favourites, restore and moves from another workspace. Built in U26f passes 3-4: a normal off-the-record Browser is a full window host. Windows of one off-the-record `Profile*` share one private workspace until the last of them closes, and nothing restores it after a clean quit or a crash; strips reach only a host of the same `Profile*`, so a private strip never reaches a regular store. It has one space with Today only; its command bar learns nothing and shows no history. Private and regular windows never see each other's workspace; moves between hosts of the same off-the-record profile are allowed, moves across profiles are refused. When a private window adopts its first tab with no active id (its page is hidden while nothing is selected), the core selects that tab in the window record only. A private window closes with its last tab; Clear removes its tabs with no toast and no Undo. Downloads from a private window go to the regular download folder without a prompt, and the private window's list is released when its last window closes. The window is always dark (`darkAqua`, sidebar included), with the masquerade mask and "Private" in the URL field and on the empty page. The checks `private-window`, `private-isolation`, `private-downloads` and `private-durability` cover this; the last relaunches cleanly and after a kill and finds none of the private titles or URLs in `workspace.sqlite`, its WAL or the profile's files. Arc's private window has not been verified (ours).

## 6. Rust core

### 6.1 Contents

- Workspace model: profile, space, container, item (tab, folder, split), archive entry, window state. Each normal space has its own favorites, pinned and Today roots. Private spaces have no favorites root. The owner chose per-space favorites on 2026-11-21.
- Tree representation: each item has one membership register `(parent id, fractional order key, HLC, previous parent id)`. Child lists are derived, never stored separately. Deterministic repair: a move that would create a cycle is resolved by keeping the move with the higher HLC timestamp and re-parenting the other item to its previous parent; items whose parent is missing go to their space's Today container, the space being found from the item's previous parent (kept in the register; a newly created item, such as a new folder or a duplicate's root, records its list root there, so a concurrent delete of its parent never carries it to another profile) or, failing that, the first space; an item whose move back to its previous parent still leaves a cycle goes to Today; delete wins over a concurrent edit unless the edit is a restore. Repair is a deterministic view over the merged registers: it never writes its result back into the registers that sync, so devices that receive the same moves in different orders compute the same tree. Only an import writes repaired registers, because the imported file is the origin of those registers. Tree-invariant tests (no cycles, every item reachable once) and delivery-order tests run on every merge test.
- Item edits: a move names a container and an index and covers reordering, pin and unpin (Today ↔ pinned), into and out of folders at any depth, favorites and back, and another space's favorites, pinned or Today. Moving a favorite to another space through its dock cell, numbered command or command bar appends the same tab to the destination's favorites. Dropping it on a specific Today, pinned or folder target moves it into that list. Moving a split member into favorites detaches it first. The core moves a folder with its subtree, though the sidebar does not start folder drags; a move into its own subtree is refused, a split moves as one, and a move that changes nothing writes nothing. Folders live in pinned only and favorites hold tabs only (Arc, `docs/research/arc-ardia-observed.md` section 8). Moving or unpinning into Today stamps the last-selected time, so auto-archive counts from the move; selecting a tab opens its closed ancestor folders; the selected tab stays selected after a move, and a move to another space does not switch the shown space. A drop between two equal order keys re-keys the tie. Moves across profiles are refused; they require a reload in the target profile and are outside phase 3 (ours). A folder can be created at a place, optionally wrapping items of one space (in outline order; split members are promoted), renamed and deleted: an empty folder is removed at once, and a folder with tabs archives them (Arc, section 8) while items that stay are re-parented to the pinned root. A tab can be renamed; the custom title shows over the page title, and an empty name clears it. Duplicate copies a tab, a folder or a favorite right after the original with fresh ids made in the core: the copy is unloaded with the same URL and titles, a folder copy keeps its order and folding and leaves out archived items inside it, and duplicating a split member copies its whole split (ours). The copy's last-selected time is the duplication time, so an old original does not make the copy archive at once; the selection, the shown space and history are unchanged (ours).
- Rules: Air Traffic Control matching exactly as measured on Arc (case, scheme and leading `www.` dropped; "Contains" also checks query and fragment; "Is equal to" compares host and path only, ignoring a trailing slash; first match wins), auto-archive thresholds, the successor-tab rule, split layout math. When the active tab changes, the outgoing tab's last-selected time is stamped at the change, so auto-archive counts from when it was last viewed; background strip changes and repeated reports of the same active tab do not restamp it (ours). Routing condition text has C0 control characters removed on add, edit and Arc import.
- Live-tab coordinator: applies engine transactions, issues commands, reconciles on start (5). FFI `live_auto_archive(window_id, now)` returns an optional `LiveBatch`; `live_delete_space(window_id, space_id)` returns a `LiveBatch`. Each batch carries the committed snapshot and a Close target (live id and pending command) for each affected loaded tab or pending open. Deleting a space archives its favorites, pinned and Today tabs. The caller closes loaded engine tabs with the command ids and cancels pending opens; unloaded rows need no engine close. Clear Today keeps its separate result because it also carries Undo information. Private workspaces skip auto-archive and reject space deletion.
- Import: Arc (`StorableSidebar`, `StorableWindows`, `StorableKeyBindings`, `StorableLinkRouting`), later Dia, Chrome, Safari, Firefox. Import builds the workspace and an import report from the Arc files, and the store writes them in one batch; Importing Chromium data such as passwords, cookies and history would write through the engine into Chrome's stores. Arc's per-profile favorites go to the first imported space of that profile in file order, retaining the tabs' IDs and order. If a profile has no imported space, its favorites are skipped. The import report gives the count for each affected profile. Arc window state (Ararat's rules; the file's shape is in `docs/research/arc-dia-components.md`): `StorableWindows.json` beside the sidebar file is optional, and a missing, unreadable, non-UTF-8 or malformed one never stops the sidebar import (the shipping flow reports unreadable, non-UTF-8 and malformed files). Folder state and tab dates come from the first window. Its `expandedItems` marks folders `expanded` (open) or `peeked` (imported closed and counted); unlisted folders are closed. Its `itemLastActiveDates` holds seconds since 2001-01-01, stored as Unix milliseconds. The report counts each folder a later window disagrees on once, peeked folders, the first window's unknown ids and malformed entries once per entry (a folder listed twice in a window keeps its last pair and can add two), future dates and dates on items that are not tabs; a tab dated twice is not counted. Arc key bindings (ours): `StorableKeyBindings.json` is read version first; an empty `userOverrides` imports nothing, and a non-empty list is counted in the report and not imported, because no non-empty list has been seen to learn its shape. Arc's Air Traffic Control rules (Arc's shapes from Cra `Sources/Cra/Model/LinkRouting.swift:8-24`, the rest ours): `StorableLinkRouting.json` beside the sidebar file is read version first; `contains` becomes Contains and `matches` Is equal to; a `space` destination with `mostRecent` becomes the most recent space and one with a known space id that space; `littleArc` becomes the Little window with the routing file's owner profile (the caller passes it; without a known owner the first space's). Profile destinations, unknown styles, destinations and space ids (an id of another profile than the owner rides in counts as unknown too; with no known owner a living space id of any profile is kept and its rule carries that space's profile, the first space's for a Most Recent or Little-window destination), malformed entries and repeated ids (the first kept) are skipped and counted; a missing file is reported as missing and a file that fails its shape check is refused and reported, and neither stops the sidebar import. Rules install in the file's order, and an empty or blank condition matches nothing (Cra `LinkRouting.swift:37`).
- Command bar ranking over sources the engine supplies (history from Chromium's HistoryService, open tabs, workspace items, commands). Built now without the engine (Cra's scores, file:line in the unit reports): one index per open, built from a repaired copy of the workspace and dropped on close; sources are open and unloaded tabs (the current one left out, favorites labelled), commands with their keys, Switch to a space other than the shown one, Go to a folder, and Move Tab to another space of the same profile (to the end of its Today, or to the end of its favorites for a favorite) or to another folder in the same profile (to the end of the folder). Choosing a favorite result switches to its owning space and selects the tab. Results are deduplicated by URL and grouped after the typed row: open tabs, history, then commands, except that the single best command whose title starts with the query at a word start comes second (U23, design's decision). An empty query lists the shown space's five most recent tabs (the current tab and favourites left out, unloaded tabs included). A private window's query gets no history rows. Queries classified as addresses by §7 open as URLs; anything else searches with `https://www.google.com/search?q=` (a constant until the engine's search engines). The typed text is a row of its own, always first, and Return runs it; at most five rows show, and commands, spaces and folders match from two characters. History is a thin HistoryService query (URL and title matches) scored in the core; there is no inline completion and no network suggestion (the Show search suggestions switch waits for the General pane). `create_tab` adds a tab at the top of the shown space's Today, selected; `set_tab_url` changes an open or unloaded tab's URL and refuses anything else.
- Sync client (8).

### 6.2 Storage

SQLite (WAL) for the workspace, archive and the sync journal. Writes run off the main thread. Cra's JSON files cost about 30 ms per write of a 2,000-item archive on the main thread before it moved writes off-main (Cra ledger 16); SQLite gives the transactions 5.2 needs.

Every record (space, item, key binding override, a profile's archive threshold, Air Traffic Control rule and default, the workspace settings such as the New Tab row switch) is one row `(kind, id, JSON body)`; spaces carry a fractional order key like items, so no list is stored. Each change is also appended to the journal table, in the same transaction. Nine kinds stay on the device and are neither journaled nor synced: `Window` (frames and sidebar state), `LittleWindow` (its frame), `LittleWindowDevice` (frame memory and hot key), `DownloadDevice` (download destination preferences), `LastSelected` (when each tab was last selected or left, which auto-archive reads), `FolderState` (which folders are closed, so folding on one Mac does not fold another), `SectionState` (which spaces' pinned sections are collapsed, for the same reason), and `HistoryPurge` and `HistoryProfile` (the history-purge outbox and the profile each tab's history belongs to). An Arc import seeds `FolderState` and, for tabs only, `LastSelected` in its batch. Rows of kinds this version does not know are kept untouched (8.3). Workspace schema version 2 requires a new database when upgrading from version 1. The writer thread commits a batch at most 1 second after its first change, with `synchronous = FULL`.

### 6.3 Bindings

- `ararat-ffi` exposes the core through UniFFI (Swift on macOS and iPhone) and a C ABI (C++ in the Chromium tree for Windows and Linux).
- The core is synchronous and owns no threads except the storage writer and the sync worker. The Swift adapter calls it from one serial queue and publishes snapshots to the UI.
- Password rows carry only metadata, and the Rust workspace core never receives passwords. An authenticated reveal borrows a UTF-16 buffer during the engine callback and puts an `NSString` in an AppKit text field while the password is visible. Add reads an AppKit secure field and inline editing reads the revealed field. Both read its value as an `NSString` and wipe the temporary UTF-16 buffer after the engine call. Ararat empties the password field and editor on Hide, on leaving the page, and on locking, closing or retargeting the pane. The Foundation `NSString` values used for add, edit and reveal, and AppKit’s field and editor copies, are outside Ararat’s wipe. The revealed text can be selected and copied with the standard macOS command. That command uses the system pasteboard and its retention rules.

## 7. macOS UI

Command bar address classification (P4): bracketed IPv6 literals, IPv4 literals, `localhost`, and bare hosts with a decimal port from 0 to 65535 use http; dotted hosts whose final label is alphabetic or a punycode label (`xn--…`) use https. Explicit URL schemes retain their scheme. Version-like text (`v1.2.3`, `1.2.3`) and invalid ports search. Absolute paths and `~/` paths become file URLs. `mailto:` and `tel:` addresses open through the OS handler; a failed handoff reports an error. Paste removes other controls first, then rejoins line breaks only when no whitespace borders an internal break and the result is an address; prose remains search text. Typed line breaks retain the search rule below. Return during IME composition commits the composition without submitting, including when the input method clears its mark before forwarding that Return.

Page fullscreen removes the sidebar, card inset and mask, and disables edge reveal. Leaving fullscreen restores the previous sidebar state. Arc's fullscreen behavior has not been observed in our notes. Engine and screen execution remain to be verified (U15, ours).

- Each space's favorites grid travels with its sidebar page when paging (B-SpacePaging).

The window follows Yab's, at Yab's measured sizes and colours (`docs/research/yab-observed.md` section 2; the owner's choice, 2026-11-02): 760 × 540 pt, a 180 pt pane list with a pill search field and 26 pt rows on a 28 pt pitch, a 52 pt toolbar with one back/forward capsule, cards of radius 12 with 10 pt gaps, and page headers (56 pt icon, title, one line) that fade into the toolbar title on scroll. Greys are neutral, not tinted by the space (ours). The list is one registry in the boards' order — General, Appearance, Websites, Tabs, Shortcuts, Air Traffic Control, Spaces, Little Window, Passwords, Privacy, Extensions, Sync, About — filtered to the panes that exist (design's decision, D1), so it shows 12 of the 13 registry panes. General, Appearance and Websites form the first rail group. The second holds Tabs, Shortcuts, Air Traffic Control, Spaces and Little Window. The third holds Passwords, Privacy and Extensions. About forms the fourth. The last three groups begin with a 14 pt gap. Sync has no page yet. A pane is a registry entry plus a view, and a pane built from U27 on groups its rows into one card per section with a 12 pt heading above it and 1 pt hairlines inset 10 pt between rows (D6), while the panes built before keep one card per row. Search replaces the pane list with results grouped by pane, the first result selected and drawn with the pane rows' selection grey in a 6 pt rounded rect; ↑ and ↓ move the selection and stop at its ends, and Return opens the selected result. A result opens its pane, scrolls to its row and fills it with the selection grey inset 3 pt at radius 9 inside its card; list rows are at least 48 pt tall, and the Spaces list keeps its 44 pt rows (D7). The Spaces pane lists spaces in sidebar order (44 pt rows: drag handle, the icon letter on a 24 pt tile, name, then the tab count and ⌃N in two fixed trailing columns so they line up down the list, and the chevron; dragging reorders); a row pushes that space's page, and on it the previous and next spaces are one slide away by arrows, dots, swipe or wheel, with the sidebar's switch spring (the owner's choice, 2026-11-03). Under the list sits one grouped card, "Scroll sideways to switch spaces", with a two-segment Natural / Reversed control and the board's caption "Reversed: scrolling right shows the space on the left" (U27c). It is one workspace setting for every device — not one per trackpad and mouse — stored in the same synced `settings` record as the New Tab row switch: Natural is the sidebar's behaviour as built (the wheel cancels the system's natural-scrolling inversion and a trackpad gesture keeps its sign), and Reversed turns the final paging direction around for both. The direction is applied once, at the start of the one pipeline both the sidebar and the settings space pages feed (`SpaceScrollState`), so the wheel's neighbours, the trackpad's follow and release, the pull past either end, and the Library's rail all turn together; the setting reaches a window's sidebar when it opens and again as soon as the pane writes it, so no relaunch is needed. Whether Natural should also follow the macOS setting (as Reversed now inverts that same behaviour) stays open for the owner's trackball check (§14). The Appearance pane (U27d, U27k) holds only the rows whose behaviour exists, in the board's order: the Theme card, a Look link row, then the Sidebar group card. The Theme row's three segments are the system's segmented control, as on the other panes (the board's E-Controls look is a starting value), in a one-row card above the Look link. Theme is System, Light or Dark, System by default, in the same synced `settings` record as the switches, so a second Mac shows the same theme; System leaves `NSApp.appearance` nil and every window follows the Mac, while Light and Dark set it to aqua or darkAqua for the whole app, so the browser windows, the settings window, popovers, menus and the command bar change together. The theme is read from the core before the first window exists and re-applied when a later window starts and at a space switch, so there is no flash of the other appearance; a private window keeps the dark appearance it forces. A space's Look still colours only the sidebar: a Look's Light or Dark applies to the sidebar alone, and a Look in Auto follows the resolved appearance for its backdrop and chooses the sidebar’s foreground from the luminance of the composited colour. Chromium's `prefers-color-scheme` follows the app's effective appearance, which the VM check proves with a fixture page rather than assumes. Page zoom waits for the engine's zoom API, so it has no row. A Look link row opens the shown space's page in Spaces, where the Look card's popover is; a Sidebar group card holds the New Tab row switch (on by default; off hides the row and the Today rows close up by its 41 pt) and the Tooltips switch (on by default; off silences every tooltip the sidebar and header draw, while menus keep their key equivalents and the controls keep their accessibility help). Both switches are in the same synced `settings` record as the scroll direction: the pane reads them on every open, a value the pane writes reaches every open window's sidebar and header at once, and a private window reads the regular workspace's record because its own starts from the built-in values. A change synced from another device reaches a window at its next space switch, where the New Tab row, Tooltips, the scroll direction and the theme are read together. The Websites pane (U27w, the E-Websites board) is engine-backed. Its first grouped card holds the seven per-permission defaults in the board's order — Camera, Microphone, Location, Notifications, Pop-up windows, Automatic downloads and Sound — with a menu per row offering only the values Chromium accepts as that kind's default: Ask / Block for Camera and Microphone (Chromium refuses Allow as a default for the media kinds), Allow / Block for Pop-up windows and Sound (their registration has no Ask), and all three for Location, Notifications and Automatic downloads. Chromium's own default prefs are written from the record and never read back as a second source, so a default changed in Chromium's own settings page is overwritten at the next start; and the core refuses a value its kind cannot take as a default, when the record is parsed and when the FFI writes it, so the pane and Chromium cannot disagree. The page's header shows the site's letter and host, and the profile's name under it when there is more than one. The site-controls popover's last row is All Site Settings… (W4), which opens this pane on the active page's origin's site page, or the list when the origin has no exception. A space's page holds Name, Icon, Look, Profile (read-only until profiles exist) and Delete Space, whose label is the board's red (#B3261E in light and #FF8A80 in dark). Look opens Yab's popover: Auto, Light or Dark per space; a polar field with hue around and lightness along the radius, one to three colour handles added and removed by − and +; the field's background is #2A2A2A in dark appearance and the control background in light (Arc's Edit Theme Color, 2026-11-05, `docs/research/arc-ardia-observed.md` section 8; light not measured); nine chips per page; a Transparency slider in percent with Glass (macOS Liquid Glass) in a socket past its end; a Grain knob; and Use for All Spaces and Reset Look in its … menu. The look is stored in Arc's terms so an Arc import edits in place: one to three colours, the colour layer's opacity (Arc's intensity maps to opacity as α ≈ 0.19 + 0.55·i per Cra's and Ardia's Arc measurements; shown as transparency = 1 − α), grain, glass and the appearance mode. Drawings, Take the site's color and Shift with tabs are left for later (the last two need pages). A space without a look uses plain sidebar vibrancy in light appearance and the Arc-measured sidebar colour (sRGB 22, 15, 31) in dark appearance, both docked and floating. Ararat keeps the default dark colour over the vibrancy while the window is inactive, a state that has yet to be measured in Arc. Deleting a space archives its open and unloaded pinned and Today items under their parents, shows a neighbour if it was shown, and is refused for the last space. The live batch carries targets; the caller closes their loaded engine tabs and cancels pending opens; the app applies the neighbour’s space and profile only when the shown space was deleted and refreshes the other windows. Arc import reads `customInfo.windowTheme`'s base colours (up to three), maps intensity to opacity as above, noise to grain and the window appearance to the mode (auto when absent); for now one look per space, so an Auto space's separate dark variant in Arc is dropped, `isVibrant` and `contentOverBackgroundAppearance` are not read, and extended-range colours are clamped to sRGB. A blended single colour (`blendedSingleColor`) imports as one colour the same way, a basic colour (`basicColor`) as one opaque colour without grain, and other background styles leave the space without a look. Look edits are not undoable (the core has no undo yet). Drawing the look (ours; Arc's mapping of handles to the gradient is not known): the colour layer sits over the vibrancy at the stored opacity, flat for one colour and a vertical gradient with stops at 0, 0.5 and 1 for two or three; grain is white specks: a generated two-octave value noise on 1.2 pt cells in one 120 pt tile that wraps, drawn as a layer whose alpha is clamp(1.4·N − 0.35) of the noise and whose opacity is the stored grain (stored 0 to 1 as Arc's noise, shown as 0 to 100 %; the mock's field, mean alpha 0.35 and standard deviation 0.16), so at 100 % the colour still shows through (the owner's choice of range and of the look at 100 %, 2026-11-11); one gain on that alpha, starting at 1, is the owner's to tune on the real app, and whether an imported Arc noise then looks as it does in Arc is not measured; Glass uses `NSGlassEffectView` on macOS 26 and later (docked it samples the window behind the sidebar, so it reads flatter than floating) and falls back to the vibrancy elsewhere; the appearance mode is applied to the sidebar, and in Auto the sidebar’s labels and glyphs use light or dark colours by the composed background's luminance (threshold 0.179, equal contrast with black and white). Unselected sidebar rows keep their usual foreground colours when they reach 4.5:1 for text and 3:1 for glyphs against the composited Look and row fill, including hover and pressed fills. Below those thresholds they use a contrasting foreground, with dimmed rows retaining as much of their dimming as those thresholds allow. Favorite icons and the Library, space dock letters and plus glyphs use the same 3:1 threshold against their own backgrounds. Selected rows, drag sources and focused split segments use the board's opaque white fill and shadow in light appearance. In dark appearance they use a 19.5% white overlay, which reproduces the measured sRGB (67, 63, 75) within one 8-bit code value per channel on the default dark background and preserves the hue of other dark Looks. During a swipe or wheel slide the colours and grain mix linearly with the page offset. Glass and explicit Light or Dark modes switch at half a page. With Reduce Transparency the colour layer draws over AppKit's opaque fallback and Glass falls back. Auto-archive follows Arc's options (12 hours, 24 hours, 7 days, 30 days; default 12 hours; per profile; no "never"; Arc's help centre article 19228855311127 and its Archive page): a Today tab archives when the time since it was last selected or left exceeds the threshold; pinned tabs, favorites and a tab selected in any window never do. Each member of a split expires on its own time. If all active members expire in the same run, the split archives as one entry (our rule; Arc has not been measured); otherwise each expired member is a separate tab entry; selecting a split stamps and protects all its members (ours). A tab with no recorded time from an older store is stamped at the next run and kept, so it expires one threshold later (ours). An Arc import keeps each tab's imported date, so an old Today tab can archive on the first run; an imported tab without a usable date is stamped at import time (ours). Restoring and becoming the close successor also stamp the time. The rule is scheduled at launch and every 60 s (20 s tolerance) in the harness and in each regular app window; private windows skip it. The live batch carries targets; the caller closes expired loaded engine tabs and cancels pending opens. A run that changes nothing writes nothing. The engine snapshot delivery and the auto-archive publish both wait while a sidebar gesture, page slide, pull, reveal, row drag or drop settle, rename or sidebar menu is in progress, and the result is delivered when that ends or at the next tick; a gesture whose end event is lost counts as ended after 2 s without scroll events or when the sidebar moves to another window. After a scroll gesture ends, a held publish waits until its momentum ends, or 0.15 s without momentum, so rows do not move while the list is still coasting (ours). ## 8. Sync

### 8.1 Model

Each normal space uses a favorites root ID derived from its space ID. Sync uses that ID for the root Item and the Space record references it.

- No account. A sync group is created on one device and backed by a 256-bit group secret, shown as a 24-word BIP-39 recovery phrase.
- The server never sees plaintext, names or secrets. It stores opaque blobs and serves them back.

### 8.2 Protocol requirements

A versioned protocol specification (`docs/sync-protocol.md`) is written and reviewed before any sync code. It must provide:

- Key schedule: HKDF from the current epoch secret (the group secret for the first epoch, a fresh random secret for each later one) into a content key, a name key and a relay key, with distinct labels (domain separation).
- Encryption: XChaCha20-Poly1305 with random 192-bit nonces, so independent devices never need to coordinate nonces. AAD binds group, epoch, device id, sequence number and object name.
- Device identity: each device has its own signing key pair; every blob is signed; devices are listed in a signed membership record.
- Pairing: a new device joins by entering the recovery phrase, or with a short code from an existing device run through a PAKE (for example CPace) so a guessed or intercepted code does not reveal the secret.
- Relay authorisation: the relay accepts writes only from registered device keys of a group and reads only with a relay credential derived from the relay key; it never holds the content key.
- Replay: each device keeps per-device sequence checkpoints and rejects blobs at or below them.
- Removal: removing a device starts a new epoch from a fresh random epoch secret, which the removing device sends sealed to each remaining device's key, never derived from the group secret alone, so the removed device cannot derive the new keys. The relay credential for the old epoch is revoked, the membership record drops the device, and remaining devices re-seal the snapshot under the new epoch. Removal also replaces the group secret: the owner is shown a new recovery phrase, and the old phrase no longer joins the group, because joining by phrase needs the current group secret. Each epoch secret is also stored on the relay sealed under a recovery key derived from the current group secret, so the current phrase alone recovers the current keys with no surviving device; the removed device cannot open it, because the group secret was replaced first. Recovery does not depend on the epoch secret it recovers: the group secret also derives, under their own labels, a recovery read credential, which the relay accepts for that sealed blob only, and a recovery signing key pair, whose public key the relay holds for the group. A device recovering by phrase reads the blob with the credential and registers its new device key with a signature from the recovery key. Replacing the group secret replaces both at the relay, so the old phrase can neither read the blob nor register a device.
- Restore safety from the first release: a device restored from backup gets a new incarnation and never reuses an incarnation or sequence number.

### 8.3 Data path

- Each device only appends: per-device logs with sequence numbers, plus periodic snapshots with version vectors. No device rewrites another device's blob.
- Merge is per-record last-writer-wins on a hybrid logical clock, with the tree rules of 6.1 applied after merge.
- Blobs are padded to 1 KiB and not compressed.
- A local journal is written before upload in the same transaction as the workspace change (5.2).
- Tombstones are kept indefinitely until device retirement, epochs and mandatory snapshot rejoin for long-absent devices exist; only then is collection allowed (Ardia ledger 3 lists the requirements its reverted attempt revealed).
- New record kinds are added under keys old versions do not read and preserve, so an older client never writes them back damaged. The iPhone client preserves record kinds it cannot use (for example extensions).

### 8.4 What syncs

Workspace, Air Traffic Control rules, key bindings, settings, passwords and Web Store extensions. Air Traffic Control rules are per workspace: one synced `routing_rule` record per rule with a fractional order key, merged put-only like items, and a `routing_default` record only once the default destination is changed (removing it restores the default). Key-binding overrides are global per command, one synced `key_binding` record each; defaults are derived and never stored, a null disables the command, and deleting the record resets it. Assigning a key clears every other holder in the same batch. When merged records give one key to several commands, the first command in the core's command table holds it and the others show no key, are marked Conflicting and still report the key they asked for; when the holder later clears, moves or resets its key, a Conflicting command takes its own key back. Reads never write. Password sync is planned. The current password store and Settings pane have the lifetimes described in §§4.8 and 6. Extensions are enabled on another device only when version and permissions match what was approved (Ardia ledger 1.5). History sync is later.

### 8.5 Server

A small Rust service: blob put/get/list per group, device-key verification, rate limits, size quotas. Storage on SQLite or an S3-compatible store. Hosting is an owner decision (14).

### 8.6 Rejected

- Chrome Sync: requires Google.
- A self-hosted Chromium sync server (Brave's `go-sync`): covers only Chromium's data types, so the workspace would need a second system, and the iPhone app has no Chromium sync engine.
- A user-chosen folder (Ardia): no folder reaches iPhone and Windows the same way; the owner chose a server.

## 10. Other platforms

- **Windows and Linux.** The same engine tree and layer. The UI is written in Chromium's Views (C++) and links the core through its C ABI; the coordinator, rules and sync are reused unchanged. On Wayland, clients cannot read the global pointer position, so the floating sidebar's outside-window rule is limited there.
- **iPhone.** App Store browsers use WebKit except in Japan (iOS 26.2+) and the EU (iOS 17.4+) under Apple's browser-engine entitlement, which requires meeting Apple's criteria including timely security updates. The iPhone app is planned on WKWebView with a SwiftUI/UIKit UI and the same Rust core and sync; Chrome extensions are not available there. A Blink build for iOS is not planned.
